# Phase 1 ルート表示UI強化: 次タスク方針

## 目的
本書は、Phase 1のルート表示UI強化における次タスクを、単独開発前提で整理するための作業方針です。

前回候補に含めていた「Jiraチケット分解」は、開発者が基本1人であるため、本フェーズでは対象外とします。
代わりに、設計ドキュメントを直接実装順に読めるようにし、個人開発で迷いが出やすい判定条件・テスト観点・UI文言の確定を優先します。

---

## 次に行うタスク（単独開発向け・優先順）

### 1. イベント契約書の実装可能化

**目的**
- イベント契約を、実装時にそのまま参照できる粒度まで具体化する。

**作業内容**
- payloadの型詳細を確定する。
- 値の単位を明記する。
- 必須/任意/null許容を明記する。
- `Success Criteria` と `Failure Modes` の判定条件を数値化する。

**完了条件**
- 各Mustイベントについて、入力値・更新状態・失敗時挙動が曖昧なく読める。
- `onNavigationTick`、`onStepBoundaryCrossed`、`onArrivalDetected` の判定条件が実装可能な粒度になっている。

---

### 2. 状態遷移図のテストケース化

**目的**
- 実装前に、状態遷移の漏れ・矛盾・戻り先の曖昧さを潰す。

**作業内容**
- 上位フロー遷移を Given / When / Then 形式に変換する。
- `navigating` サブ状態を重点的にテストケース化する。
- フロア跨ぎ・逸脱・中断・到着の境界ケースを明文化する。

**完了条件**
- `idle -> searching -> options -> preview -> navigating -> arrived` の正常系がテスト仕様化されている。
- `off_route`、`transitioning_floor`、`paused_confirm` の戻り先が明確になっている。

---

### 3. UI文言・表示ルールの固定

**目的**
- 距離・時間・フロア跨ぎ情報の見え方を統一し、実装時の判断を減らす。

**作業内容**
- 距離表記ルールを決める。
- 時間表記ルールを決める。
- フロア表記ルールを決める。
- フロア跨ぎ通知・逸脱通知・到着通知の文言テンプレートを作る。

**完了条件**
- `120m`、`1.2km`、`約3分`、`B1 -> 1F` などの表示ルールが統一されている。
- Bottom Sheet / Chip / Indicator で使う文言が揃っている。

---

### 4. 計測イベントの最小設計

**目的**
- Phase 1のUI改善が効果を出したかを、最低限の指標で確認できるようにする。

**作業内容**
- ルート検索開始率を計測する。
- ルート開始率を計測する。
- 到着完了率を計測する。
- フロア跨ぎ通知表示回数を計測する。
- 逸脱検知回数を計測する。

**完了条件**
- 各計測イベントについて、event名・発火条件・payload最小項目が定義されている。

---

## 今回やらないこと

### Jiraチケット分解

**理由**
- 開発者が基本1人であり、チケット分割の運用コストが開発効率を上回るため。

**代替方針**
- Jiraではなく、Markdown上で「次に読む順」「次に実装する順」が分かる構成にする。
- 必要になった時点で、Mustイベント単位のチェックリストへ分解する。

---

## 推奨する直近の着手順

1. `route-ui-event-contract.md` のMustイベントに、payload詳細と判定閾値を追記する。
2. 状態遷移図を Given / When / Then 形式のテスト仕様に変換する。
3. UI文言・表示ルールを固定する。
4. 最小限のAnalyticsイベントを定義する。
