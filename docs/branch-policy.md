# ブランチ運用方針

この文書は、短命ブランチや復旧用ブランチが長期間残り、統合済み・未統合の判断が難しくなることを防ぐための運用基準です。

## 基準ブランチ

- `develop`: 日常の統合先であり、GitLab のデフォルトブランチとする。
- `main`: v1.0 など、リリース対象として検証済みの内容だけを集約する。
- 作業ブランチから `main` へ直接統合せず、原則として `develop` を経由する。

## 作業ブランチ

利用できる接頭辞は次のとおりです。

- `feature/*`, `fix/*`, `hotfix/*`
- `docs/*`, `chore/*`, `refactor/*`, `test/*`
- AI エージェントが作成する短命ブランチ: `codex/*`, `claude/*`

作業ブランチは目的ごとに1本とし、マージまたは作業中止後に削除します。同じ目的の自動生成ブランチを複数残しません。

## 復旧データの扱い

- `recovery/*` ブランチは作成しない。
- 未統合コミットを保全する必要がある場合は、`archive/YYYY-MM-DD/<元ブランチ名>` 形式のタグを使用する。
- 復旧内容を統合するときはブランチ全体をマージせず、現在の要件に必要なコミットだけを新しい作業ブランチへ取り込む。
- 取り込み後は、元ブランチと重複する復旧ブランチを削除する。

`.gitlab-ci.yml` の `branch-policy-check` は、この規則に反するブランチ名を検出します。

## v1.0の機能範囲を判断する基準

v1.0の機能範囲は、既存UIに残っている導線ではなく、`docs/api-foundation.md` を含むv1.0方針文書を正とします。

管理者ポータルのQR発行・QRチェックイン関連UIは、QR依存機能をv1.0で提供する前提だった時期の実装を含みます。これらが残っていることを、v1.0の主要機能として採用する根拠にはしません。QR issue、ワンタイムコード、参加者識別、チェックイン状態管理は主要導線へ再導入せず、正式対応はv1.1以降に再設計します。

Issue #4の整理では、マップ画面復元コミット `1e5e358` だけを取り込み、QR hidden beta画面への導線を復元するコミット `7324a8c` は取り込みません。

## マージ前後の確認

1. 対象ブランチの未統合コミットと変更ファイルを確認する。
2. 現在の方針と重複または矛盾する古い実装を取り込まない。
3. ビルド、型検査、関連テストを実行する。
4. マージリクエストを通して `develop` へ統合する。
5. 統合済みの作業ブランチを削除する。
6. 未統合作業を破棄する場合は、必要に応じてarchiveタグを作成してから削除する。
