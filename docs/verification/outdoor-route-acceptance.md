# iOS 主要屋外5経路の受け入れテスト（#79・E9-4）

この手順では、参加者が公開版の iOS アプリで選んだ屋外経路を、実際に歩いて目的地までたどれるかを確かめます。経路ごとに、試験前に確定した ID 列・通行条件・距離・徒歩時間と、配信値・画面表示・現地実測を照合します。現在は手順と記録書式を用意した段階です。正式な受け入れには #32・#33 の実データ、Studio からの公開、#85 の操作導線が必要です。[#79](https://github.com/m0o9l0v3/NexusMobile/issues/79)

## 1. 位置付けと対象範囲

対象は4章の主要屋外5経路です。2026-11-23 の改定で、E5（#36、#38〜#44）の屋内フロアマップ、階切替、屋内目的地強調、同一階・階層間・屋内外接続の経路案内は v1.0 リリース後に移りました。[v1.0 スコープ正本](../v1.0-scope.md#主要屋外経路)・[#33](https://github.com/m0o9l0v3/NexusMobile/issues/33)・[#223](https://github.com/m0o9l0v3/NexusMobile/issues/223)・[PR #224](https://github.com/m0o9l0v3/NexusMobile/pull/224)

実習棟（`ptb`）は #16 で屋外直結の正式入口の登録対象外です。参加者が屋外だけで到達できる地点を現地確認し、基準データに正式登録できた場合に別途追加できます。現行5経路に含めず、教室棟（`mb`）の正式入口で OR-5 を終えます。そこで実習棟に到着したとは記録しません。[入口データの扱い](../../map-data/README.md)

| 担当 | 確かめること |
| --- | --- |
| #32・#33 | #32 が実測した屋外グラフを整備し、#33 が5経路の正式な経由点・通行条件・期待値を確定します。 |
| #79（本文書） | 公開された経路を実機で選び、線・ステップ・要約と現地の歩行結果を照合します。 |
| [#76 の探索テスト](../implementation/issue-76-routing-engine-tests.md) | グラフ構築、目的地の解決、方向・重み・通行制約と探索結果を単体で検証します。 |
| [#80 の実機確認](ios-gps-battery-check.md)・[#78 のアクセシビリティ監査](ios-a11y-check.md) | #80 は GPS の精度・鮮度・電池消費を測ります。#78 は読み上げ・文字サイズ・操作性などを監査します。 |
| [#87](https://github.com/m0o9l0v3/NexusMobile/issues/87) | 各記録を集約し、統合試験、TestFlight 実機での再確認、旧実装整理とその後の再確認を統括します。 |

## 2. 守ること

- 試験の前に #33 の期待値・許容差と根拠の版を凍結します。実行後に基準を見直す場合は理由と新しい版を残し、別の回で再試験します。
- 現地の結果には、公式に公開された実測データと、その版を使った実機歩行の記録を使います。合成データ、配信例、地図の下書きから正式な期待値や結果を転記しません。
- 公開記録には承認済み ID、版、測定条件、集計値、証跡の管理番号を使います。緯度・経度、平面直角座標、ローカル絶対パス、原本固有の識別子、個人の実名を記載しません。写真・画面・ログの扱いは7章に従います。

## 3. 準備段階と正式版合否の区別

**段階 A（公開前の準備）** では次の条件を確認し、8.2 に根拠を記録します。この段階では正式版の合否を付けません。

| 試験前にそろえるもの | 完了を確認する根拠 |
| --- | --- |
| #32 の測量・GeoJSON 確定 | 独立測量後の始終点、正式入口、屋外ノード・歩行辺、方向・通行属性、距離・秒数を追跡できる確定版。 |
| #33 の期待値凍結 | 5経路すべてについて8.4を記入し、通行条件ごとに比較できること。許容差・計時方法・凍結日時・根拠版を含めます。 |
| Studio からの公開 | 確定した地図を含む公式 bundle を参加者向け接続先から取得でき、#33 の根拠版と照合できること。 |
| #85 のアプリ操作 | 現在地と手動の出発地を選べること、位置情報を拒否しても手動で続行できること、始点変更時に目的地が維持されること。検索・案内・地点詳細から同じ ID で経路確認へ進めること。 |

本手順作成時（コミット `67d08e7`）の本番構成は `RouteRequestHandling.bundle` に公開データの参照元を渡します。既定出発地は `nil`、出発地選択 UI は未実装です。目的地が解決できても始点がなければ「出発地が設定されていません」と表示します。`.accessibleOnly` の UI 切替も未接続です。試験版で #85 の導線と #33 が採用した各条件の実行方法を確認し、操作できない項目は保留にします。[アプリ構成](../../apps/nexus-ios/Nexus/Application/NexusApp.swift)・[公開 bundle の経路要求](../../apps/nexus-ios/Nexus/Features/Route/Data/RouteRequestHandling+Bundle.swift)・[#85](https://github.com/m0o9l0v3/NexusMobile/issues/85)

DEBUG の `-NexusRouteCheck <found|samePoint|disconnected|unreachable|notRoutable|unknown|unavailable>` は、山括弧内から1つ選んで通知・表示や操作順のリハーサルに使えます。#76 の単体テストや [participant-bundle-v2.example.json](../schemas/examples/participant-bundle-v2.example.json) も仕組みを確認するためのものです。リハーサルの結果は正式版の実施記録に含めません。

**段階 B（公式データ公開後の受け入れ）** では、同じ公開版に対して6.1の事前照合、6.2の5経路の操作と現地歩行、6.3の異常系・境界確認を行い、7章で判定します。正式版の操作は合成シナリオの起動引数を外して行います。

### 4.1 建物と入口台帳で確認できること

建物 canonical ID と表示名は E1-1（表示名の最終決定 C-012、2026-11-02）、入口と屋外ノードの ID 体系は E1-2 に従います。下表右側は #16 の正規化入口台帳にある屋外ノードとの先行対応（PR #221）です。公開版で各経路が使う始終点は別途 #33 で確定します。[建物 ID と表示名](../decisions/E1-1-building-canonical-ids.md)・[階層 ID](../decisions/E1-2-hierarchical-ids.md)・[入口台帳](../../map-data/normalized/entrances.csv)・[PR #221](https://github.com/m0o9l0v3/NexusMobile/pull/221)

| 建物 ID | 表示名 | 台帳の入口 ID | 台帳の屋外ノード ID |
| --- | --- | --- | --- |
| `ctc2` | CTC2 | `ctc2_ent_001` | `campus_n_006` |
| `hgr_a` | 格納庫A | `hgr_a_ent_001` | `campus_n_020` |
| `hgr_b` | 格納庫B | `hgr_b_ent_001` | `campus_n_021` |
| `mb` | 教室棟 | `mb_ent_001` | `campus_n_008` |

格納庫AとBは別の入口・別の屋外ノードへ接続する方針です。4入口とも `floor_id`・`inside_node_id`・`is_primary` は空欄、`accessibility` は `unknown` です。`status` は最初の3件が `measured_connections_pending`、教室棟が `coordinate_confirmed_connections_pending` です。いずれも独立測量した座標に置き換え、接続情報を確定してから公開します。[地図データの出典と公開条件](../../map-data/README.md)

### 4.2 下書きで確認できること（段階 A）

- ノードは30行のうち有効25点です。`retired` は `campus_n_011`、`campus_n_016`、`campus_n_018`、`campus_n_019`、`campus_n_025` の5点です。正門は `campus_n_001`（`junction`）で、駐車場に該当するノードは未登録です。E1-4 改訂1 §5 により、`outdoor_node` の ID をそのまま Spot ID には使えません。[ノード下書き](../../map-data/drafts/campus_nodes_draft.csv)・[目的地 Feature と到達ノード](../decisions/E1-4-r1-destination-features.md)
- 辺は37行のうち有効29本、`retired` 8本です。`distance_m` は全37行で空欄（未測量）です。有効辺はすべて `bidirectional=true`。階段は `campus_e_025`（`campus_n_010` ↔ `campus_n_022`）の1本で、`path_kind=stairs`・`accessibility=not_accessible` です。他の28本は `path_kind=walkway`・`accessibility=accessible` です。[辺の下書き](../../map-data/drafts/campus_edges_draft.csv)
- 下書きの接続だけをたどると、通常歩行・車いす条件の両方で正門から有効25点すべてに到達できます。現地での通行可否と最短経路は測量・確認を待ちます。旧資料の `road_arena_ctc_pk`（148 m 記録）は区間ずれのため不採用が確定しています。[下書きの確認記録](../../map-data/drafts/README.md)

### 4.3 現行 iOS の探索・表示規則

| 項目 | 比較に使う規則 |
| --- | --- |
| 通行条件 | `RoutingOptions` の `.standard` は `accessible`・`not_accessible`・`unknown` を通行可とし、`.accessibleOnly` は `accessible` だけを通します。既定の評価指標は距離優先です。[探索の決定記録](../decisions/E4-2-routing-engine.md) |
| 要約距離 | 選んだ辺の配信値 `distance_m` を合計し、座標から再計算しません。`RouteSummaryFormatter` は 0 を「0 m」、正の値は m に丸めた値が 1000 未満なら 1 m 単位（最小「1 m」）、それ以上なら km で小数1桁（`%.1f km`）にします。[要約の実装](../../apps/nexus-ios/Nexus/Features/Route/Models/RoutePresentationModels.swift) |
| 徒歩の目安 | 配信値 `estimated_seconds` の合計を使います。0 は「0分」、正で60秒未満は「1分未満」、60秒以上は分に丸めて「約X分」、丸め後60分以上は「約X時間Y分」（余り0分なら「約X時間」）です。[ポリラインと要約](../implementation/issue-34-route-polyline-summary.md) |
| 屋外のステップ | 方向判定で 0.5 m 未満の微小線分を除外します。向きの変化が25°未満なら直進にまとめ、25°以上45°未満は「やや右／左へ進む」、45°以上150°未満は「右／左へ曲がる」、150°以上は「折り返す」です。現地評価前の表示基準です。[ステップの実装](../../apps/nexus-ios/Nexus/Features/Route/Models/OutdoorRouteStepModels.swift) |
| 目印・行の距離 | 同じノードでは `landmark` の Spot 名、`formal_entrance` 名、名前付き `outdoor_node` 名の順に選びます。各行の距離は次の指示までの距離を個別に丸めるため、行の表示値の合計と要約距離に差が出る場合があります。[屋外ステップの実装記録](../implementation/issue-35-outdoor-route-steps.md) |

## 6. 受け入れテスト手順

### 6.1 B-1 公開データ（bundle）の事前照合

1. 対象の公開 bundle を取得し、8.1 の版と #33 の凍結版を照合します。以下を OR-1〜OR-5 の各適用条件で行い、8.3 に記録します。
2. 始終点について、Spot の ID と対応する目的地 Feature の ID・種別・所属を突き合わせ、到達ノードを解決します。`landmark` は屋外の `destination` ノード、屋外から向かう `formal_entrance` は外側ノードです。`building` は明示した到達ノードが優先で、指定がない場合だけ唯一の代表入口の外側を使います。入口の場合は公開版の `outside_node_id` と、所属する階・内側ノード・代表入口フラグ・通行属性も照合します。実際に解決した点が #33 指定の屋外側かを確認します。必須経路の到達ノード欠落は、公開時に警告扱いでも見逃さないでください。[E1-4 改訂1 §4・§8](../decisions/E1-4-r1-destination-features.md)
3. 凍結した順に各 `walking_path` の端点・進行方向・双方向性・屋外区間・通行属性をたどります。各辺の `distance_m`・`estimated_seconds` が有限の正数であることを確認し、それぞれ合計します。8.4 の未丸め合計と、4.3 で丸めた表示期待値に一致するか記録します。[GeoJSON の歩行辺](../decisions/E1-4-geojson-schema.md)
4. 同じ公開 GeoJSON を `RoutingGraph.build(from:)` で読み、`skippedDiagnostics` の対象 ID と理由を確認します。固定した始終点・評価指標・通行条件で探索し、返ったノード列・辺列（向きを含む）と合計を8.4に照合します。対象経路の辺が除外され、別の経路で到着できても一致とはしません。照合結果を取得できない項目は保留にします。

### 6.2 B-2 主要屋外5経路の正常系試験

OR-1〜OR-5 を、8.4 で採用した条件ごとに次の順で行います。現地で画面を操作するときは立ち止まり、計時中の停止を凍結した方法で扱います。

1. 現地の正式な始点に立ち、検索または案内から目的地の地点詳細を開きます。名称と ID を確認し、「経路を確認」へ進みます。#85 の手動選択で凍結した始点を指定し、現在地を使う条件では同じ始点ノードに解決したことを確認します。権限拒否時の手動選択も確認し、使った導線・条件を記録します。
2. Map に始点・終点マーカーと進行方向どおりのポリラインが出ることを確認します。「全体を表示」を押して両端と全経路を見渡し、8.3 の分岐順・屋外通路と照合します。要約の出発地・目的地、距離・徒歩時間の表示文字列を8.5に写します。[Map の表示](../../apps/nexus-ios/Nexus/Features/Map/Views/MapRootView.swift)・[経路要約カード](../../apps/nexus-ios/Nexus/Features/Route/Views/RouteSummaryCardView.swift)
3. 「屋外のステップ」を展開し、出発、各分岐の方向と目印、到着が進行順であることを確認します。一覧を閉じて開き直します。同じ目的地で出発地を変更し、目的地が維持され、マーカー・線・要約・ステップが新しい経路に更新されるかを見ます。正式な試験始点に戻して経路・条件を再確認します（OR-1 と OR-2 は同じ受付を使えます）。[ステップ一覧](../../apps/nexus-ios/Nexus/Features/Route/Views/RouteStepListView.swift)
4. 案内中に別地点の詳細を開き、目的地が変わらず「経路へ戻る」で元の経路全体と要約に戻れるか確認します。別タブから Map に戻っても同じ経路と手順を読めることを確認します。[案内状態の保持](../../apps/nexus-ios/Nexus/Features/Route/State/RouteRequestStore.swift)
5. 始点で距離計を合わせ、出発時刻を記録します。屋外の指示を順にたどり、現地の分岐・左右・目印・段差・通行可否と照合します。指定の屋外到達点で停止し、到着時刻、実測距離と歩行時間、停止・迂回の有無を記録します。閉鎖や危険で通れない場合はその場で中断し、地点 ID・理由を残します。
6. 到着点と終点マーカーの対応を記録して「案内を終了」を押します。経路線・経路用マーカー・要約・ステップ・案内先が消えることを確認し、7章に従って8.5に判定を記入します。

### 6.3 B-3 異常系・境界確認

公式版で条件を満たす入力と操作経路を先に特定します。独立した実行記録を残すため、必要な場合は直前に正常な経路を表示します。OR-E1〜OR-E5 では通知の理由、要求元のタブ、直前の案内が置換されていないことを確認します。公開データに該当例がない、または要求を入力できない場合は保留とし、下書きや DEBUG の結果で埋めません。[通知の実装](../../apps/nexus-ios/Nexus/Features/Route/Views/RouteRequestNoticeView.swift)

| ID | 操作 | 期待結果 |
| --- | --- | --- |
| OR-E1 | 既知の同じ到達ノードを始終点に指定します。 | 同一点で移動不要と分かります。探索上は距離・秒数とも0、ステップなしで、新しい通常経路は表示されません。 |
| OR-E2 | 向き・通行制限を外しても別の連結成分になる既知の2点を指定します。 | 未接続（`disconnected`）の説明が出て、直線で結んだ案内を表示しません。 |
| OR-E3 | 同じ連結成分で、向きまたは適用する通行条件により全経路が通れない組合せを指定します。 | 通行不可（`unreachable`）の説明が出ます。禁止辺や直線による代替案内はありません。合法な迂回路がある組合せはこの入力から除きます。 |
| OR-E4 | 公開済みで到達ノードを解決できない既知の目的地を指定します。`ptb` は公開版でこの条件に該当する場合に使います。 | 経路対象外（`notRoutable`）と理由が分かり、別の入口や教室棟に案内しません。 |

## 7. 判定基準・失敗時の判定と証跡

| 判定 | 付ける条件 |
| --- | --- |
| 合格 | 正常系では同一版・同一条件の ID 列、配信値、画面、現地通行、実測の許容差がすべて期待どおりです。異常系では6.3の入力条件を確認し、該当する期待結果をすべて観察できました。 |
| 不合格 | 確定した期待値に反する結果を観察しました。誤到着、通行条件違反、対象の辺・重みの不整合、表示の不一致、適正に測定した現地値の許容差超過などを該当 ID に記録します。 |
| 保留 | 未確定値、版の不一致、必要な操作や観測の不足、臨時閉鎖・測定中断などにより判定できません。どの条件がそろえば再試験できるかを残します。 |
| 未実施 | 対象項目にまだ着手していません。書式の初期値です。 |

比較は次の3段階で行います。

1. **配信値と探索結果**。事前に凍結した順序付きノード列・辺列、方向、評価指標・通行条件と一致するかを確認します。同じ辺列の配信値合計（m、秒）と探索結果の未丸め合計を比較します。
2. **配信値と画面表示**。距離と時間の合計をそれぞれ4.3の規則で表示文字列に変換し、アプリの要約と一致するかを判定します。ステップ行の距離は各区間で個別に照合します。
3. **配信値と現地実測**。同じ始終点・経由列・通行条件で、実測距離と未丸めの期待距離、実測歩行時間と未丸めの期待秒数の差を求めます。8.4で凍結した単位・比較式・境界に照らし、距離と時間を個別に判定します。測定区間や停止の扱いが異なる場合は理由を残して再測定します。

失敗時は影響を記録します。別の棟への誤案内、危険区間や通行不可区間への誘導は**重大**として歩行を中止します。必要な経路を表示できない、指示や値が基準から外れる場合は**主要**、到達・通行判断に影響しない表記上の所見は**軽微**とします。重大度と合否は別々に記録します。

| 最初に差が出た箇所 | 確認先 |
| --- | --- |
| 現地と公開地図の形状・接続・属性・辺の重み | #32（測量・データ）、#33（5経路の定義・許容差） |
| 配信データ上は正しいが解決ノード・順序・通行条件・探索合計が違う | #37（目的地解決・探索）。#76 の該当テストも照合します。 |
| 探索結果は正しいが線・マーカー・要約・丸め表示が違う | #34（ポリライン・要約） |
| ステップの順序・方向・距離・目印が違う | #35（屋外ステップ） |
| 出発地選択・タブ間の受渡し・版保持・状態復帰が違う | #85（操作統合）。開始時と失敗時の版と要求元を添えます。 |

証跡には試験 ID・回・版・操作順、期待と実際、集計値、必要箇所だけの画面または診断記録を残します。原本（写真・測量記録・未加工ログ）はアクセス制限した非公開領域に保管します。公開する画面は位置情報・個人情報・端末通知・画像の位置メタデータを除去し、公開表には匿名の証跡番号で対応付けます。
