# E8-4 r1: 構内 NAT 下でのログ送信の rate limit

## 0.1 決定（2026-11-14 利用者決定）

- **N-1a：iOS v1.0 は参加者ログを送らない。** ログ送信の上限は今の値のまま据え置く（L-0）。`/api/logs`・`/api/logs/batch` と上限の設定は残す。
- 将来 iOS にログ送信を加えるときは、本書の §2.2・§2.3 と L-1 を出発点に、上限の値をその時点の事実から決め直す。
- 判断の材料として利用者から示された事実：**オープンキャンパスの参加者など一般の来場者は、構内 Wi-Fi に接続できない**。構内 Wi-Fi を使うのは在校生・教職員だけである。したがって、参加者の端末が構内の NAT で1つの外向き IP にまとまる、という #107 の前提は成り立たない。参加者の端末はキャリアのモバイル回線から届く。キャリアの CGNAT で IP を共有することはありうるが、1つの IP に集まる台数は構内 Wi-Fi の NAT より少ないと考えられる。
- この事実は、E2-5 §4.1.2（bundle の GET に rate limit をかけない理由）の「構内 Wi-Fi の NAT」の記述にも関わる。bundle の GET に上限をかけない決定（O-9 L1）は、CGNAT でも同じ理由で維持できるため、変えない。

## 0. 要約

いま、本番の public-api にログを送るクライアントは**無い**。旧 PWA は 2026-10-25 に削除され、iOS アプリ（`apps/nexus-ios`）はログ送信を実装していない。したがって、構内 NAT で 429 になる問題は、**iOS v1.0 がログを送ると決めたときに初めて起きる**。

推奨は、まず「iOS v1.0 がログを送るか」（N-1）を決めること。送らないなら上限は今のまま据え置き（L-0）、送るなら iOS はまとめ送りだけを使い、IP 単位のまま上限の値を実測した人数から決める（L-1）。上限の値は、構内の外向き IP の構成と当日の人数を確かめるまで決めない。

### 1.3 1つの IP に何台まで載るか（式）

当日の人数を推測で書かないため、式だけを示す。

- 1台がまとめ送りを `T` 秒に1回行うとき、1つの外向き IP の後ろにいる `N` 台が1分間に送る回数は `N × 60 / T`。
- 今の `log-ingest-batch` の上限（12 回 / 60 秒）に収まる台数は `N ≤ T / 5`。
  - 例：`T = 300` 秒（5分に1回）なら 60 台、`T = 60` 秒なら 12 台。
- Fixed Window なので、窓の境目をまたぐと短い間に最大で2倍まで通る。逆に、端末の送信がそろう（アプリを前面に戻した直後など）と、平均より多くの要求が1つの窓に集まる。

## 2. 選択肢

### 2.1 まず決めること：iOS v1.0 はログを送るか（N-1）

| 案 | 内容 | 影響 |
|---|---|---|
| N-1a：送らない | v1.0 の iOS はログを送らない。`/api/logs` は残すが、使うクライアントが無い | 429 の問題は起きない。上限は今のまま（L-0） |
| N-1b：送る | 目的（例：混雑の把握、案内の改善）と送る項目を決め、iOS に実装する | 以下 L-1〜L-4 から上限の決め方を選ぶ。端末側の規則（§2.3）も要る |

### 2.2 上限の単位と値（N-1b の場合）

| 案 | 内容 | 長所 | 短所・リスク |
|---|---|---|---|
| L-0：据え置き | 今の値（60 / 12 回 / 60 秒 / IP）のまま | 変更なし | N-1b で構内の台数が `T / 5` を超えると、正当な来場者のログが 429 で落ちる |
| **L-1：IP 単位のまま、まとめ送りの上限を実測から上げる** | iOS は `/batch` だけを使う。`log-ingest-batch` の `PermitLimit` を、確認した最大台数と送信間隔から決め、余裕を持たせる。値は環境変数で変える | コード変更が無い（設定だけ）。当日でも値を変えられる。今のテストの形のまま確かめられる | 1つの IP の上限を上げると、構外の1台からも同じ回数まで送れる（乱用の余地が広がる） |
| L-2：構内の外向き IP だけ上限を変える | 構内の IP（CIDR）を設定に持ち、そこからの要求だけ別の上限を使う | 構外からの乱用の余地を広げない | コード変更が要る。学校の IP を設定に持つ必要がある（値は Git に書かず、保護された運用記録と秘密の設定に置く）。IP が変わると効かなくなる |
| L-3：IP 単位の緩い上限＋全体の上限 | IP ごとの上限を緩め、別に全クライアント合計の上限を置いて DB を守る | NAT の影響を受けにくい。DB への書き込みの総量を抑えられる | コード変更が要る。全体の上限に達すると、乱用した1者のせいで全員が落ちる |
| L-4：端末ごとの ID で数える | 匿名のインストール ID（ヘッダー）で分ける | NAT の影響を受けない | ID は偽装できるので、IP の上限も残す必要がある。端末を長く識別する値を新たに持つことになり、個人を特定しない粒度の方針（`CLAUDE.md`）と緊張する。**推奨しない** |

### 2.3 端末側の規則（N-1b の場合、どの案でも要る）

- まとめ送り（`/batch`）だけを使い、1件ずつの `POST /api/logs` は使わない。
- 送る間隔に端末ごとのばらつき（jitter）を入れ、アプリを前面に戻した直後などに送信がそろわないようにする。
- 429・503 では `Retry-After` に従う（E2-5 §6 規則10 と同じ考え方）。
- 送れなかったログは端末に上限付きで溜め、古いものから捨てる。ログが落ちても画面の動作に影響させない。

## 3. 推奨

1. **N-1 を先に決める。** v1.0 のリリース条件にログの用途が無いなら **N-1a（送らない）＋ L-0（据え置き）** とし、本 Issue は「iOS がログ送信を加えるときに L-1 で値を決める」と記録して閉じる。
2. **N-1b（送る）なら L-1 を採る。** iOS は `/batch` だけを使い、§2.3 の規則を守る。上限の値は §5 の事実（外向き IP の数と、1つの IP に載る最大台数）と送信間隔 `T` から §1.3 の式で決め、2倍程度の余裕を持たせる。値と根拠を本書に追記する。
3. **L-2・L-3 は、L-1 で足りないと分かったとき（実測で 429 が出た、または乱用を観測した）の予備策として記録する。** L-4 は採らない。
4. いずれの場合も、隔離環境で `RateLimitingTests` が通ることを確かめ、本番への適用は NexusInfra の手順と承認を経る。隔離環境での成功を本番適用済みとは扱わない（#107 の受入条件）。

理由:
- いまログを送るクライアントが無く、送らないなら変更の必要が無い。必要の無い仕組みを先に作らない。
- 送る場合も、L-1 は設定の変更だけで済み、当日に値を直せる。1名の保守体制でコードを増やさずに済む。
- L-4 は個人を特定しない方針と緊張し、偽装もできるため、得るものに対して負担が大きい。

## 4. 選ばなかった案

| 案 | 選ばなかった理由 |
|---|---|
| L-0 を N-1b でも続ける | 構内の台数が `T / 5` を超えると、正当なログが落ちる |
| L-2：構内 IP の別扱い | 学校の IP を設定に持つ必要があり、変わると効かない。L-1 で足りない場合の予備策とする |
| L-3：全体の上限 | コード変更が要る。DB の負荷が問題になったときの予備策とする |
| L-4：端末 ID | 偽装でき、端末を識別する値が増える。個人を特定しない方針と緊張する |
| rate limit を外す | 認証なしの書き込みエンドポイントを無制限にすると、DB への書き込みを外から増やせる |

### 実機・学校のネットワークで確かめる事実（推測で埋めない）

2026-11-14 の決定（§0.1）により、以下は**iOS にログ送信を加えると決めたときに**確かめる。参加者が構内 Wi-Fi に接続できないことは利用者が確認済みである。

値は Issue・PR・本書に貼らず、保護された運用記録に残す（#107 の作業内容）。本書には「確認済み」と確認日だけを書く。

- 構内 Wi-Fi は NAT か。来場者の端末が外に出るときのグローバル IP の数。
- 来場者用と、教職員・在校生用のネットワークが分かれているか（分かれていれば、来場者だけの台数で考えられる）。
- 当日の想定来場者数と、同時に構内 Wi-Fi に接続する端末の最大数（受付の記録・過去の開催の実績）。
- モバイル回線（キャリア）の CGNAT でも同じ IP を共有しうるが、構内 Wi-Fi に比べて1つの IP に集まる台数は少ないと考えられる。必要なら #80 の実機検証で 429 が出ないか確かめる。
- 構内のプロキシが TLS を中継していないか（E8-1 §5 と一緒に確かめる）。
