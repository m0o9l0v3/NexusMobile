# M1: 正式データによる地点表示の範囲と暫定判断

- 区分: マイルストーン M1（v1.0 の中間到達点）
- 状態: **起案**（2026-10-23、技術的意思決定者の判断をもとに作成。本書のマージをもって採用とする）
- 前提の決定: [E2-5](E2-5-participant-data-delivery-v2.md)（配信契約 v2）、[E1-4 改訂1](E1-4-r1-destination-features.md)、[E1-7](E1-7-room-canonical-ids.md)、[E1-3](E1-3-spot-id-integration.md)、NexusStudio #4（公開・復旧の Studio への一本化）
- 関連 Issue: #23、#109、#24、#26、#85、#84、#31、#28、#21、#16、NexusStudio#11、NexusInfra#8・#17

本書は M1 の受入範囲と、上位の Issue で正式に決まるまでの暫定判断を記録する。E2-5 などの採用済み契約は変えない。

## 1. M1 の到達目標

Studio で公開した正式な地点情報が、安全で整合した単一の版として iOS に届き、Map 上で正しい地点として選択・閲覧できること。

経路探索（M2）、屋内外・階層間の案内（M3）、実機統合試験・TestFlight（M4）は M1 に含めない。v1.0 の必須範囲から外すという意味ではない。

## 2. 決定事項

| ID | 論点 | 結論 | 関係先 |
|---|---|---|---|
| M1-1 | 受入で表示を求める地点の範囲 | **14棟の建物 Spot は全件の表示を必須とする。** 部屋・ランドマークは、Studio で公開したものがすべて正しい位置・ID で表示されることだけを求め、件数は受入条件にしない | #16、#26、#85 |
| M1-2 | `delivery` スキーマの置き場所と public-api の接続 | **`studio`・`delivery` とも、admin-api・public-api が共有する同じデータベース（`public` スキーマのあるデータベース）に置く。** 本番では NexusInfra の契約B（`pg17-baseline.md`）が定める PG17 の `nexus` データベースを指す（§3 の食い違いを参照）。public-api は既存の単一の接続（本番は `nexus_public`）のまま、`delivery` の2表だけを SELECT する（スキーマの USAGE と2表の SELECT を付与）。接続文字列は増やさない。E2-5 §3.1 の前提（`delivery` は `studio` と同じデータベース）とも一致する。<br>・**起動時の検査**：`DatabaseReadiness` が照合する移行履歴は admin の `public.__EFMigrationsHistory`（2本）であり、Studio の移行履歴は `studio.__EFMigrationsHistory` に分かれる（Studio の `StudioDbContextOptions`）ため、`delivery` の追加で履歴の検査は変わらない。権限の検査（`public` への CREATE が無いこと等）も変わらない。public-api の起動時に `delivery` の2表の存在を検査するかは #23 で決める | NexusInfra#8・#17、#23 |
| M1-3 | iOS の配信 API の接続先の注入 | **ビルド構成ごとの xcconfig に `NEXUS_API_BASE_URL` を置き、Info.plist 経由で読む。** 値が空なら従来どおり「未接続」で起動する。秘密情報は置かない。xcconfig は `//` から行末をコメントとして扱うため、URL は `https:/$()/example.com` のように `//` を分けて書く。ビルド構成ごとに、生成された Info.plist の値が完全な URL であることを試験で確かめる | #109 |
| M1-4 | M1 の実データを Studio に入れる経路 | **地図と Spot の両方を、レビュー済みのファイルから管理コマンドで取り込み、Validator を通してから Release で公開する。** Map Editor の目的地 Feature の追加・移動（ME-16・ME-17）の画面は、Figma Phase 2 の後に回す。<br>・**地図**：目的地 Feature を含む GeoJSON 2.0.0 を、新設する取り込みコマンド（または API）で入れる。<br>・**Spot**：GeoJSON の `room` / `landmark` は名前を持たない（E1-4 改訂1 R-7）ため、地図から Spot を作らない。Studio の既存の参照データ取り込み（`ReferenceImporter`、運用者が明示的に実行するコマンド）を使い、14棟（E1-1）と E1-7 の新 ID の Spot を、名前・検索別名・種別とともに入れる。種別・説明文の項目は NexusStudio#11 の Spot モデルの変更に合わせて取り込み形式へ加える（説明文は O-2d により null）。<br>・**公開**：各 Release で生成される bundle が E2-5 §5.3 の不変条件を満たすように、地図と Spot の公開の順序（同じ Release にするか、地図を先にするか）を NexusStudio#11 の射影の実装で決めて検証する | NexusStudio#11 |
| M1-5 | 地図の描画方式 | **SwiftUI の MapKit（`Map`・`MapPolygon`・`Annotation`）を前提に進める。** 外部 SDK は追加しない。#24 の「外部タイル不通でも構内図を表示できる」条件は、通信断で建物の形・ラベル・ピンが表示されることの確認として #24 で検証・記録する（§3） | #24、#26 |
| M1-6 | #84 の承認と UI 実装の開始条件 | **M1 で使う画面だけを先に部分承認してもらう。** 対象は Map（S02）と地点詳細（S03）、その読込・空・失敗・保存版・未掲載の状態で、node ID・承認者・承認日を記録する。経路・案内の画面は #84 全体の承認を待つ | #84、#85、#31 |
| M1-7 | 新しい版を受信したときの表示の切替（E2-5 §6 規則5） | **暫定：保存はすぐ行うが、表示中の Map は開いた時点の bundle（snapshot）を保持し、地図・ピン・地点詳細をすべてその同じ snapshot から解決する。** 旧版の地図を表示している間に新しい版が保存されても、その後に開く詳細も含めて保存ポインタを読み直さない（地図は旧版で詳細だけ新版、という混在を作らない）。Map タブを開き直したとき、または詳細を閉じたときに、地図・ピンを含む Map 全体の snapshot を最新の保存版へ切り替える（詳細だけを切り替えることはしない）。手動の再読み込みは M1 では作らない。正式な扱いは #84・#85 で決める | #85、#84、#109 |

## 3. 既存の記載との食い違い

- **#24**：本文は「描画方式を比較・採用する」「特定 SDK は検証・決定前に確定しない」としている。M1-5 は比較を省き MapKit を前提にした。MapKit は OS 標準のフレームワークであり外部 SDK の追加はないが、#24 の完了条件を「比較」から「MapKit の採用記録と通信断時の表示の検証」に改める。個別成果の受入条件の正本は各 Issue である（`docs/v1.0-scope.md`）ため、本書だけで読み替えた状態にせず、**#24 の本文に受入条件の更新を追記した（2026-10-23）。** 通信断で構内図が表示できないと分かった場合は、本判断を見直す。

- **本番データベースの方針**：nexus-mobile の [`production-database.md`](production-database.md)（2026-09-19）は PostgreSQL 18・データベース名 `nexus_admin` を採用としているが、その後の NexusInfra の契約B（`pg17-baseline.md`、Issue #7 で隔離検証済み）は、既存 VPS の PostgreSQL 17 の `nexus` データベースに admin・public のスキーマを作る経路を定めている。M1-2 はどちらの場合も「public-api が接続している同じデータベースに置く」とし、データベース名には依存しない。`production-database.md` を契約B に合わせて改めるかは本書の範囲外とし、別の PR で判断する。→ **2026-10-25 に解消**：`production-database.md` §0 で、第1段階を既存 PG17 の `nexus`（契約B）、第2段階を PG18 とする2段階に改めた（利用者決定）。

## 5. M1 の受入条件

受入条件は、実データで行う統合受入（5.1）と、実データでは再現しにくい場合を各 Issue の試験で確かめるもの（5.2）に分ける。M1 の完了は、5.1 の証跡と 5.2 の試験結果をそれぞれの Issue に対応付けて判定する。

### 5.1 統合受入（隔離環境で、Studio の公開操作から iOS シミュレーターの表示まで）

隔離環境は NexusInfra の契約B と同じ構成（PG17・Caddy）とする。照合の基準は、そのとき iOS が保存した bundle（同じ snapshot）の内容とする。

1. **建物**：14棟の建物 Spot がすべて表示され、14棟それぞれについて canonical ID・位置・建物の形状（Polygon）・ラベル（`building.properties.name`）が bundle と一致する（件数だけで判定しない）。
2. **部屋・ランドマーク**：公開したものがすべて、bundle と同じ canonical ID・位置で表示される。
3. **選択と詳細**：14棟それぞれと、公開した部屋・ランドマークのそれぞれについて、表示を選ぶと同じ canonical ID の地点詳細が開く（1地点の確認で済ませない。自動化した UI 試験で全件を辿ってよい）。
4. **詳細の内容**：ピン（Annotation）と地点詳細の地点名が `spots[].name` と一致する（E2-5 §5.2 の表示名の正本。建物のラベルとは別に照合する）。`placement` のある地点では、詳細の建物名・階名が同じ bundle の `building.properties.name`・`nexus.floors[].name` と一致する。既知の種別は `spots[].kind` と一致する。
5. **版の切替**：版 N の Map を表示中に、Studio で公開した版 N+1 が保存されても、地図・ピン・詳細は版 N のまま表示される。そのうえで、詳細を閉じた後と Map タブを開き直した後のそれぞれで、Map 全体が版 N+1 に切り替わる（M1-7。最初の snapshot を保持し続ける実装を合格にしない）。
6. **保存版の表示**：通信を切った状態で、Map と地点詳細が保存版として表示され、`bundle_version`・`published_at`・最終確認日時（E2-5 §6 規則7）が実際の値どおりに表示される。
7. **保存版がない初回起動**：クリーンインストール直後に、まだ公開がない（404）場合は「掲載なし」、通信できない場合は「失敗」の状態（M1-6 で承認した表示）になり、読込中のまま止まらず、fixture や別の地点を代わりに表示しない。

### 5.2 各 Issue の試験で確かめるもの（fixture・試験用サーバーで再現する）

| 場合 | 確かめること | 担当 |
|---|---|---|
| 304 | 失敗ではなく「最新であることの確認」として扱い、失敗の表示を出さず、最終確認日時（規則7）と次回確認までの間隔（`Nexus-Recheck-After`、規則10）を更新する | #109 |
| 破損・照合ヘッダーの欠落・版の後退・未知のメジャー版・硬い上限の超過 | bundle を採用せず、保存済みの版を表示し続ける。保存版がない場合は 5.1-7 と同じ失敗の状態になる | #109 |
| 書き込み途中の終了 | 本体・メタデータ・ポインタのそれぞれの書き込み途中でプロセスを終了させても、再起動後に版が混在せず、直前の正常な版を表示できる（E2-5 §6 規則3） | #109（PR #110 の試験を含む） |
| 種別が null・未知の値 | 種別を表示せず、既存の種別（`facility` など）に置き換えない（E2-5 §5.2、O-2c） | #109 |
| bundle の外から来た ID | 完全一致 → alias で1段 → 未掲載の順で解決し、未知・未公開の ID を別の地点に置き換えず「未掲載」と表示する（E2-5 §6 規則11）。M1 では bundle の外から ID を渡す画面がまだ接続されないため、統合受入ではなく解決器と `MapContentClient` の試験で確かめる | #109 |
| 接続先の注入 | ビルド構成ごとに、生成された Info.plist の `NEXUS_API_BASE_URL` が完全な URL である（M1-3） | #109 |

### 5.3 扱い

- fixture での表示を、Studio から正式データが届いたことの証跡にしない。5.2 の試験は iOS の振る舞いの確認であり、5.1 の代わりにしない。
- 隔離環境での成功を本番適用済みとは扱わない。
- M1 の完了をもって #85 は Close せず、`main` へもマージしない。
