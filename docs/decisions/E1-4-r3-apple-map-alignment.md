- 改訂対象:

  - [E1-5](E1-5-coordinate-reference-system.md)（座標系）の「何に位置を合わせるか」
  - [E3-1](E3-1-mapkit-adoption.md)・[M1 決定記録](M1-scope-and-interim-decisions.md) M1-5 の「通信断でも建物の形を表示する」条件
  - [E1-4 改訂1](E1-4-r1-destination-features.md) §4.2（航空神社）
- 状態: **起案**（判断待ち。§8 の H-1〜H-6）
- 起案日: 2026-11-12
- 起点: 改訂2 の iOS 実装（PR #150）を見た利用者が、手作りの描画を足しすぎると画面のまとまりが無くなるとして、Apple の地図を前提に建物の形を描き直す方向を選んだ（2026-11-12）
- 関連: E2-5（配信契約）、NexusStudio 決定事項31（地図の公開判定）・34（実データ Spot の種別）、#24、#26、#28

## 1. 何が変わったか

改訂2 では、Apple の地図の建物と Nexus の建物の形のずれを、構内に不透明な地面を描いて Apple の地図の建物を隠すことで解決するとした。iOS の実装（PR #150）まで進めたが、利用者は次の理由で方向を改めた。

- アプリが描く要素（地面・建物の枠と塗り・ラベル・ピン）が多く、Apple の地図の上に別の地図を重ねたような、まとまりの無い画面になる。
- 利用者が Apple の純正のマップアプリで確かめたところ（2026-11-12）、構内の14棟はすべて建物として、3D モデルとともに Apple の地図にあった。航空写真（地理院タイル）に写っていなかった7棟（改訂2 §2）も含む。無いのは航空神社だけだった。

Apple の地図に建物がそろっているなら、Apple の地図を地図として使い、アプリは「どれを選んだか」だけを示せばよい。ずれは、Nexus の建物の形を Apple の地図に合わせて描き直して解消する。

## 2. 判断の要点

| 項目 | 改訂2 まで | 本書（案） |
|---|---|---|
| 位置を合わせる基準 | 実際の位置（航空写真で確かめる）。Apple の地図には合わせない（改訂2 §2） | **Apple の地図**（§3） |
| 構内の地面 | 不透明に描いて Apple の地図の建物を隠す | **描かない**。改訂2 を取り下げ、2.1.0 を戻す（§6） |
| 建物の形の表示 | 常に青い枠と塗り | **選んだ建物にだけ枠を出す**（§4） |
| 建物の選び方 | 建物の Spot のピンから | ピンに加え、**建物そのものをタップして選べる**（§4.2） |
| 通信断のとき | 建物の形が見える（M1-5、E3-1） | H-4 で決める（§4.3） |
| 航空神社 | `campus_lm_001` として地図・Spot に載せる | **実データから外す**（§5） |

座標系そのもの（RFC 7946 の WGS 84、`[経度, 緯度]`、小数6桁、屋内の相似変換）は変えない。変わるのは、建物などの形を「何に合わせて描くか」だけである。

## 3. 位置を Apple の地図に合わせる

### 3.1 理由

- 来場者が見るのは Apple の地図である。画面の建物と、選んだときの枠・ピンが合っていることが、測量としての正しさより体験に効く。
- 改訂2 §2 で比べたずれは数 m だった。スマートフォンの GPS の誤差は屋外でもおおむね 5〜10 m あり、ずれと同じか大きい。今後の現在地の表示（Apple の地図の上の青い点）で、実際の位置に合わせたことの利点はほとんど見えない。

### 3.2 すべての位置を同じ基準で描く

建物だけを合わせると、ほかの位置と食い違う。地図のデータに入るすべての位置を、Apple の地図に合わせて描く。

| データ | 扱い |
|---|---|
| 建物（`building`） | Apple の地図の建物の形に合わせて描き直す（作業はオーナー、H-2） |
| 正式入口（`formal_entrance`） | 描き直した建物の辺に置く。`map-data/normalized/entrances.csv` の写真の GPS は、どの辺のどのあたりかの根拠として残し、座標をそのまま採らない |
| 屋外ノード・経路（`outdoor_node`・`walking_path`） | Apple の地図の道に合わせて置く（#16・#39 で作るときから） |
| 屋内のアンカー（E1-5） | 描き直した建物の角など、Apple の地図に合わせた位置を基準にする（#36 で作るときから） |

Studio の検証（`entrance_connection_gap`・`path_distance_mismatch` など）は、すべてが同じ基準で描かれていれば、これまでどおり働く。

### 3.3 Apple の地図が変わったとき

Apple の地図は予告なく直ることがあり、こちらでは気付けない。オープンキャンパスの前など、公開の前に、シミュレーターで建物と Apple の地図の建物が合っているかを目で確かめる。ずれていれば、そのとき描き直す。

### 3.4 Apple の利用規約の確認（H-1）

Apple の地図を見ながら建物の形を写し取ることが、Apple の利用規約で認められるかを、描き直しの前に確かめる。MapKit・Apple Maps の規約には、地図の内容を取り出したり、別の地図データを作ったりすることを制限する条項があると考えられる（本書の起案時点では原文を確かめていない）。

認められないと分かった場合の代わりは次のとおり。

- 航空写真・基盤地図情報（国土地理院）から描き、Apple の地図とのわずかなずれは受け入れる。選んだときの枠は、細い線や角丸で、ずれが目立ちにくい見た目にする（G-5 と同じく Figma で決める）。
- Apple の地図からは形を写し取らず、建物ごとの平行移動の量だけを目で合わせる。これも規約の範囲かを同時に確かめる。

## 4. 表示

### 4.1 建物は選んだときだけ枠で示す

- ふだんは建物の形を描かない。建物は Apple の地図の建物（3D を含む）を見せる。
- 地点を選んだとき（ピンのタップ・建物のタップ・検索・地点詳細から）、その地点が所在する建物を枠で囲う（今の強調、#28 と同じ判定）。
- 建物のラベルとピンは、ひとまず今のまま残す。Apple の地図が構内の建物名を出すか、ラベルと重なるかは、描き直した後にシミュレーターで確かめ、必要なら見直す。
- `.mapStyle(.standard(pointsOfInterest: .excludingAll))` は変えない。3D の建物を見せるかどうか（`elevation`）は、Figma で見た目を決めるときに合わせて決める。

### 4.2 建物をタップして選ぶ

SwiftUI の `Map` では、Apple の地図の建物そのものはタップを受け取れない（`MapFeature` で選べるのは施設などで、建物は含まれない）。タップした位置を地図の座標に変え（`MapReader`）、Nexus の建物の形の内側かどうかをアプリで判定し、その建物の Spot を選ぶ。ピンのタップと同じく、Map タブが地点詳細を開く。

形が Apple の地図に合っていれば、Apple の建物のどこをタップしても当たる。以前、建物のラベルを選べる部品にしたときは、ピンの地点名と重なってタップを受け取れなかった（#145）。この方法はラベルに頼らない。

### 4.3 通信断のとき（H-4）

E3-1・M1-5 では、通信断で地図タイルが読めなくても、建物の形・ラベル・ピンが見えることを条件にした（#24 で検証）。建物を描かなければ、通信断ではラベルとピンだけが方眼の上に残る。オープンキャンパスの当日は、人が集まって携帯の回線が混みやすい。

| 案 | 内容 | 画面のまとまり | 通信断 |
|---|---|---|---|
| A（推奨） | 建物を、枠の無いごく薄い塗りで常に描く。色は Apple の地図の建物に近いものにする | 通信があるときは Apple の建物とほぼ重なり、目立たない | 建物の形が見える。E3-1 の条件を保つ |
| B | 建物を描かない | 最もすっきりする | 建物の形は見えない。E3-1 の条件を改め、#24 の受入条件の更新も要る |

A の塗りの色は、選んだときの枠と合わせて Figma で決める。

## 5. 航空神社を外す

航空神社は Apple の地図に無く、合わせる元が無い。オープンキャンパスの案内との関わりも薄い。実データから外す。

| 場所 | 扱い |
|---|---|
| `tools/map-dataset/config/campus-buildings.config.json` | `landmark_coordinates` の取り込み元と `campus_lm_001` の Feature を外す。旧 ID `lm_koku_shrine` の除外の設定も不要になる |
| `map-data/normalized/landmark-coordinate-review.csv`・`map-data/README.md` | 消さずに、採用しないことを記録する（改訂1 §4.2 から参照されている） |
| NexusStudio `deploy/reference/spots.json`・決定事項34 | 実データの Spot から外し、決定事項34 に外したことを追記する |
| 改訂1 §4.2 | 本書で外したことを追記する |

変えないもの:

- Feature 種別 `landmark` と ID の形式 `campus_lm_{seq:03}`。将来、屋外の目印を足すときに使える。
- テスト・JSON Schema の正常例の `campus_lm_001`。ランドマークという種別の一例として使っているだけで、実データではない。

ID の予約（E2-5 §5.5）: 本番で `campus_lm_001` を公開したことがなければ、予約は無く、外すだけで済む。公開したことがあれば、廃止した ID として予約に残り、再利用できない（H-5）。

## 7. 取り込む順序

1. 本書の判断（§8）。H-1（規約）が先
2. iOS の試作：2〜3棟だけ Apple の地図に合わせて描き直したデータで、§4 の表示（選んだときの枠・建物のタップ・H-4 の案）をシミュレーターで確かめる
3. §6 の取り下げと戻し（mobile・Studio）
4. §5 の航空神社の除外（mobile・Studio）
5. オーナーが14棟を描き直す（§3.2）

## 9. 却下した選択肢

| 選択肢 | 却下の理由 |
|---|---|
| 改訂2 のまま（地面で Apple の地図の建物を隠す） | アプリが描く要素が多く、画面のまとまりが無くなる（§1） |
| Apple の地図に合わせず、選んだときだけ枠を出す | 枠を出したその建物で、Apple の建物とのずれが見える。端をタップすると Nexus の形から外れ、選べないことがある |
| 常に建物の枠と塗りを描く（今の表示） | ずれが常に見え、画面も重い |
| 航空神社を残し、Apple の地図に無いまま置く | 合わせる元が無く、オープンキャンパスとの関わりも薄い。残す手間に見合わない |
