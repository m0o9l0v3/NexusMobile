# E1-2: 建物・フロア・経路ノード・正式入口の階層 ID を定義する

- 移行元ID: E1-2 / 区分: E1
- 依存: E1-1（`docs/decisions/E1-1-building-canonical-ids.md`）
- 判断日: 2026-09-03
- 判断者: リポジトリオーナー（技術的意思決定者）
- 状態: 採用

## 採用方針

E1-1 で確定した14棟の `canonical_id` を階層の起点とし、次の ID 形式を採用する。

| 対象 | 形式 | 例 | 採番範囲 |
|---|---|---|---|
| 建物 | `{building_id}` | `mb` | E1-1 の14棟をそのまま使用 |
| フロア | `{building_id}_{floor_code}` | `mb_1f`, `mb_b1f` | 建物ごと |
| 屋内経路ノード | `{floor_id}_n_{seq:03}` | `mb_1f_n_001` | フロアごと |
| 屋外経路ノード | `campus_n_{seq:03}` | `campus_n_001` | キャンパス全体 |
| 正式入口 | `{building_id}_ent_{seq:03}` | `mb_ent_001` | 建物ごと |

ID はすべて ASCII 小文字の lower_snake_case とする。`seq` は `001` から始め、`000` は使用しない。

階層は ID の見た目だけに依存せず、データ上の親参照を正とする。`ctc_main` や `hgr_a` のように建物 ID 自体がアンダースコアを含むため、ID を `_` で分割して親を推測してはならない。

## エンティティごとの規則

### 建物 ID

建物 ID は E1-1 で確定した次の14件に限定する。

`ab`, `amh`, `aptr`, `ar`, `ctc_main`, `ctc2`, `dh`, `dvh`, `hgr_a`, `hgr_b`, `lbh`, `mb`, `ptb`, `sab`

- `building_` 接頭辞を追加しない。
- 表示名、略称の意味、GeoPackage の旧 `code` 列から ID を再生成しない。
- 新しい建物を追加するときは、既存の全エンティティ ID と衝突しない canonical ID を別の判断記録で確定してから使用する。

### フロア ID

`floor_code` は、地上階を `{number}f`、地下階を `b{number}f` で表す。

- 有効例: `1f`, `2f`, `12f`, `b1f`, `b2f`
- 無効例: `1F`, `01f`, `floor_1`, `ground`, `地下1階`
- `floor_code` の正規表現: `^(?:[1-9][0-9]*|b[1-9][0-9]*)f$`
- フロア ID は、登録済み `building_id` と `floor_code` を `_` で連結する。
- `building_id` を必須の親参照として保持し、`floor_id` の接頭辞と一致することを検証する。
- 屋上、塔屋、中間階など、この規則で表せない階を経路対象にする場合は、推測でコードを追加せず規則を拡張する判断を先に記録する。

表示用の `1F`、`地下1階` などは名称フィールドに保持し、ID には使用しない。

### 経路ノード ID

経路ノードは屋内と屋外で名前空間を分ける。

- 屋内ノードは `floor_id` を親とし、`{floor_id}_n_{seq:03}` とする。
- 屋外ノードはキャンパス全体を単一スコープとし、`campus_n_{seq:03}` とする。
- 屋内ノードは `building_id` と `floor_id`、屋外ノードは `scope=campus` を明示的に保持する。
- `seq` は各フロア、またはキャンパス全体のスコープ内で一意にする。
- ノードの用途、座標、接続順、施設名は ID に埋め込まない。
- 一度公開したノード ID は、座標調整や接続辺の変更では変えない。ノードの分割・統合で廃止した ID は再利用しない。

屋外ノードを最寄り建物の配下に置かない。建物間の通路、分岐点、道路横断点は単一の建物に属さないためである。

### 正式入口 ID

正式入口は経路ノードとは別の永続エンティティとし、`{building_id}_ent_{seq:03}` を使用する。

正式入口は最低限、次の参照を持つ。

| フィールド | 必須 | 規則 |
|---|---|---|
| `id` | 必須 | `{building_id}_ent_{seq:03}` |
| `building_id` | 必須 | E1-1 の建物 ID |
| `floor_id` | 必須 | 当該建物に属する入口階 |
| `outside_node_id` | 必須 | `campus_n_{seq:03}` の屋外ノード |
| `inside_node_id` | 必須 | `floor_id` 配下の屋内ノード |

- `main`, `north`, `受付側` などの名称・方角・役割は ID に埋め込まず、別フィールドで管理する。
- 入口 ID と内外ノード ID を同一にしない。入口設備の同一性と、経路グラフの分割・再測量のライフサイクルを分離するためである。
- 正式採用前の候補入口や調査点を published データの canonical ID として登録しない。調査元 ID は移行対応表に保持する。
- 正式入口を廃止しても ID は再利用しない。後継入口には新しい連番を割り当てる。

## 共通の一意性・不変条件

1. published MapDataset 内では、エンティティ種別をまたいで `id` が全体一意であること。
2. ID の比較は大文字小文字を区別し、正規形は ASCII 小文字のみとすること。
3. 親参照先が存在し、フロア、屋内ノード、入口の親子関係が一致すること。
4. 正式入口の `outside_node_id` は屋外ノード、`inside_node_id` は同じ `floor_id` の屋内ノードを指すこと。
5. 同じ親スコープ内で連番が重複しないこと。欠番は許可し、詰め直さないこと。
6. 公開済み ID は不変とし、改名が必要な場合は新 ID と旧 ID の alias／移行対応を記録すること。
7. 表示名変更、座標補正、データ配列順の変更を理由に ID を変更しないこと。

連番が `999` を超える場合は桁数を暗黙に拡張せず、互換性への影響を確認したうえで本規則を改訂する。v1.0 の対象規模では3桁で十分と判断する。

## 具体例

教室棟 `mb` の1階に正式入口が1つある場合:

```text
building:     mb
floor:        mb_1f
outside node: campus_n_021
inside node:  mb_1f_n_004
entrance:     mb_ent_001
```

正式入口 `mb_ent_001` は `building_id=mb`、`floor_id=mb_1f`、`outside_node_id=campus_n_021`、`inside_node_id=mb_1f_n_004` を参照する。

実習棟 `ptb` の地下1階に屋内ノードを置く場合:

```text
building: ptb
floor:    ptb_b1f
node:     ptb_b1f_n_001
```

## 採用理由

- E1-1 の短い固定建物コードを変更せず、そのまま後続データの親キーにできる。
- ID だけでも所属範囲を人が確認しやすく、同時に明示的な親参照で機械的な整合性検証ができる。
- 屋内と屋外のノード名前空間を分けることで、構内経路と建物内経路を同じグラフへ安全に接続できる。
- 正式入口をノードから分離することで、入口名称や正式指定を保ったまま経路グラフを再測量・再分割できる。
- 名称・方角・座標を ID に含めないため、表示変更や測量補正で参照が壊れない。
- 3桁固定連番により、ソート、目視確認、正規表現検証が単純になる。

## 却下した選択肢

- **全エンティティを UUID にする**: 全体一意性は得られるが、調査データ・レビュー・障害調査で所属を確認しにくく、決定的な変換も難しいため却下。
- **種類別の全体連番だけにする（`floor_001`, `node_000123`）**: 親スコープが ID から判別できず、データ結合時の誤参照を見つけにくいため却下。
- **表示名や方角を含める（`mb_main_entrance`, `mb_north_door`）**: 表示名・正式指定・方角の見直しで ID 変更が発生するため却下。
- **入口と経路ノードに同じ ID を使う**: 入口設備とグラフノードの更新周期が異なり、ノード分割・統合が入口 ID を不安定にするため却下。
- **屋外ノードを最寄り建物配下にする**: 建物間の分岐や道路横断点の親が恣意的になり、建物をまたぐ経路で重複・付け替えが発生するため却下。
- **フロアに表示値 `1F` をそのまま使う**: E1-1 の lower_snake_case 方針と一致せず、大文字小文字や日本語表記の揺れを持ち込むため却下。
- **既存 Phase 1 モックの `1f`、`entrance`、`room-a` を canonical ID として維持する**: 建物スコープがなく、14棟を統合したときに一意性を保証できないため却下。

## 既存実装との関係

`apps/public-api/Data/phase1-navigation.json`、`apps/mobile-ios/src/components/map/mockData.ts`、Public API の現行 DTO には、`1f` / `2f`、`entrance`、`room-a` のような建物スコープを持たない Phase 1 モック ID と、表示値 `1F` / `2F` が残っている。

これらは本決定の canonical data ではない。後続の MapDataset スキーマ・基準データ・変換作業で本規則へ移行し、旧 ID との対応表を残す。本Issueでは既存 API、DTO、モックデータを変更しない。

## 後続Issueが前提にできる事項

- MapDataset の各エンティティは `id` に加え、上記の親 ID・参照 ID を明示的に保持する。
- validator は ID 形式、全体一意性、親の存在、親子整合、入口の内外ノード種別を検証する。
- 構内経路と屋内経路は、正式入口が参照する `outside_node_id` / `inside_node_id` を介して接続する。
- 変換処理は入力順や座標から連番を毎回振り直さず、確定した対応表を使用して同じ入力から同じ ID を生成する。
- E1-1 の旧建物 ID、既存モック ID、実地調査元 ID は canonical ID と混在させず、alias／移行対応表で扱う。

## 本Issueのスコープ外

- 各建物の実フロア一覧と、全ノード・全入口の具体的な採番
- 正式入口の選定、名称、開閉時間、バリアフリー属性、座標
- GeoJSON／MapDataset の完全なスキーマ、座標参照系、経路辺 ID の規則
- 既存 GeoPackage、GeoJSON、API、iOS モック、DB のデータ移行
- E1-1 で保留された `ptb` provisional feature の置換 ID

これらの具体データや実装は後続Issueで扱うが、そこで使用する建物・フロア・ノード・正式入口 ID の形式について追加の命名判断は不要とする。
