# E6-6: 案内タブの原稿はアプリに内蔵して届ける

- 移行元ID: E6-6 / 区分: E6 / Issue: [#49](https://github.com/m0o9l0v3/NexusMobile/issues/49)
- 関係: #51〜#54（各原稿）、#86（案内画面と案内詳細）、#83（データ供給元・運用責任）、E2-5（参加者向け公開データ配信契約 v2）§11 O-2d
- 判断日: 2026-11-13（供給方式 A は利用者決定）
- 判断者: リポジトリオーナー（技術的意思決定者）
- 状態: **起案**。本書の PR のマージで、§1〜§4 を採用とする。§5 の未決事項は採用後も未決のまま残り、記載の期限までに決める

## 1. 決定

案内タブの原稿（学科・寮・学校生活・アクセス・受付・困ったとき・施設利用・FAQ・注意事項）は、**リポジトリ内のファイルとして持ち、アプリに同梱して届ける（案A）**。

- 原稿の変更は PR でレビューしてから入れ、アプリの更新（TestFlight / App Store）で参加者に届く。
- 配信 API・Studio の編集画面は v1.0 では作らない。
- iOS の取得境界 `GuidanceClient` はそのまま残し、内蔵の原稿を読む実装を加える。将来 API 配信（案B）へ移るときは、この境界の実装を差し替える（§4）。

## 2. 対象の分け方

| 情報 | 供給元 | 理由 |
|---|---|---|
| 学科・寮・学校生活・アクセス・受付・困ったとき・施設利用・FAQ・注意事項 | **アプリ内蔵（本決定）** | 開催回ごとに変わらない、または変わる頻度が低い |
| 開催時間・受付時間・展示・プログラムなど、開催回に依存する情報 | **Studio のイベント公開** | 開催回ごとに変わり、当日に直す必要がある。案内の原稿には書かず、必要ならイベント側の表示へつなぐ |
| 地点の名前・種別・説明文 | **Studio の Spot 公開（E2-5）** | 本決定で変えない。説明文の担い手は §5 U-1 と同じ決定に従う（U-2） |

案内の原稿に開催回固有の日時・時間を書かない。書くと、Studio で直しても案内側が古いまま残るためである。

## 3. 通信がないときの振る舞い

- 案内は、通信の有無にかかわらず**同じ画面・同じ内容で読める**。通信断のための専用の状態や画面は作らない。
- 変わるのは次の3点だけである。
  - **更新状況の表示**：内蔵の原稿は通信で受け取らないため、「オフライン保存版」「最新確認不可」は案内の原稿には当てはまらない。代わりに**原稿の確認日**を表示する（§5 U-3 で Figma を直す）。
  - **外部リンク・電話**：公式サイトなどのリンク先は通信がないと開けない。原稿の保存とは別に扱う（#86）。
  - **開催回に依存する情報**：Studio から届く情報は、端末に保存した最後の版を表示する（E2-5 の規則のまま）。
- 検索：現在の検索（探すタブ）の対象は地点だけで、保存済みの bundle を使うため通信なしでも動く。**案内の本文は検索の対象にしない**（#86 の対象外「案内全文横断検索の無承認追加」のまま）。対象に加える場合は別に判断する。内蔵の原稿なので、加えても通信なしで検索できる。

## 4. 原稿ファイルの最小の取り決め

形式と置き場所の詳細は #86 の実装で決める。どの形式でも、記事ごとに次を持たせる。

| 項目 | 内容 |
|---|---|
| 記事ID | 大文字・小文字を保持する識別子（`GuidanceArticleID`）。表示名から作らない |
| 記事の種類 | `GuidanceArticleKind`（standard / help / helpHealth / access / faq）。レイアウトは種類で決め、ID で分岐しない |
| 本文 | 見出しと段落（`GuidanceSection`） |
| 関連地点 | canonical ID。確定していない地点は書かない（無反応のボタンを出さない） |
| 出典 | 元にした資料の名前と日付、または原稿の提供元 |
| 確認日・確認者 | 誰がいつ内容を確認したか（役割でよい）。画面の「確認日」はここから出す |

確認日・確認者・出典のない原稿は、公開合格にしない（#86 の受入条件「正式原稿必須の項目が欠けた版を公開合格にしない」）。

### 案B へ移るとき

当日の修正がアプリの審査待ちでは間に合わない、という事態が実際に起きた場合に見直す。そのときは E2-5 の bundle に案内記事をマイナー版で加え、Studio に編集と公開前検証を作る。§4 の項目を bundle の項目にそのまま写せるように、内蔵の原稿の形式を決める。

## 5. 未決事項

| ID | 論点 | 決める人 | 期限 |
|---|---|---|---|
| U-1 | 原稿の担い手：学校から公式資料・原稿を提供してもらうか、オーナーが書いて学校に精査してもらうか、オーナーが公式資料から転記して自分で確認するか。あわせて、確認者・更新担当を決める | オーナー（学校側との相談による） | #51〜#54 の原稿作成を始める前 |
| U-2 | 地点の説明文（E2-5 O-2d）の担い手。U-1 と同じ体制にするかどうか | オーナー | U-1 と同時。決まるまで説明文は公開しない（NexusStudio 判断記録29 M1-D1 の取り決めのまま） |
| U-3 | Figma の Guidance/Common/UpdateStatus（`2720:5366`）を「原稿の確認日」の表示に改める | オーナー、Figma 担当 | #86 の実装前 |

U-1 が決まるまでも、画面の実装（#86）と原稿ファイルの形式は進めてよい。ただし、仮の原稿や Figma の仮の情報（仮の駅名・運行間隔など）を正式な原稿として入れない。

## 6. 選ばなかった案

| 案 | 選ばなかった理由 |
|---|---|
| B：Studio で編集し、E2-5 の bundle で配信する | アプリの更新なしで直せ、公開経路を Studio に一本化できる。しかし Studio に記事の編集画面・公開前検証を新たに作る必要があり、作業量が最も大きい。原稿の多くは開催回ごとに変わらず、当日に直す必要がある情報は §2 のとおりイベント側にある |
| C：内蔵の原稿を初回用に持ち、以後は B で更新する | 初回からオフラインで読めて当日も直せるが、内蔵と配信の両方の仕組みと、どちらの版を表示するかの規則が要る。保守できる人が1名の体制（`CLAUDE.md`）では負担が大きい |
