## 2. 規則

```text
{building_id}_{floor_code}_{type}_{seq:03}
```

| 要素 | 規則 | 例 |
|---|---|---|
| `building_id` | E1-1 の14棟に限る | `mb`、`ptb`、`ctc_main` |
| `floor_code` | E1-2 と同じ（`{n}f` / `b{n}f`） | `1f`、`2f`、`b1f` |
| `type` | §2.1 の閉じた集合 | `cl`、`cr`、`wc`、`rm` |
| `seq` | `001` から。`(building, floor, type)` の組の中で一意。3桁固定（R-012） | `001` |

- `{building_id}_{floor_code}` は E1-2 の `floor_id` と完全に一致する。部屋 ID は常に自分の `floor_id` を接頭辞に持つ。
- 室の用途・名称・番号は ID に入れない（E1-2 と同じ理由）。名称が変わっても ID は変わらない（E1-3 規則5）。
- 比較は大文字小文字を区別する完全一致とし、lower_snake_case を正規形とする（E1-3）。

### 2.1 型コード

| code | 意味 | 件数（対応表） |
|---|---|---|
| `cl` | 教室 | 8 |
| `cr` | 廊下 | 2 |
| `wc` | トイレ | 20 |
| `rm` | 上記以外の室（実習室・事務室・諸室など） | 44 |

型を追加する場合は、本書を改訂してから使う。実装側は閉じた集合として検証する。E1-4 改訂1 の `room.properties.room_type` はこの集合と同じである。

型コードは **ID 構造のための分類**であり、参加者向けの種別（E2-5 §5.2 の `kind`）ではない。`kind` を型コードから導出しない（E2-5 O-2 K1）。

### 2.2 他の ID との判別

| 対象 | 形式 | 判別子 | 正本 |
|---|---|---|---|
| 建物 | `{building}` | 型セグメントなし | E1-1 |
| フロア | `{building}_{floor}` | 末尾が `f` | E1-2 |
| 屋内ノード | `{floor_id}_n_{seq:03}` | `n` | E1-2 |
| 屋内辺 | `{floor_id}_e_{seq:03}` | `e` | E1-4 |
| 正式入口 | `{building}_ent_{seq:03}` | `ent` | E1-2 |
| 屋外ノード | `campus_n_{seq:03}` | `campus_` ＋ `n` | E1-2 |
| 屋外辺 | `campus_e_{seq:03}` | `campus_` ＋ `e` | E1-4 |
| ランドマーク | `campus_lm_{seq:03}` | `campus_` ＋ `lm` | E1-4 改訂1（R-4） |
| **部屋** | `{floor_id}_{cl\|cr\|wc\|rm}_{seq:03}` | `cl` `cr` `wc` `rm` | **本書** |

型コード `cl` / `cr` / `wc` / `rm` は `n` / `e` / `ent` と重ならず、末尾が `f` でないためフロア ID とも区別できる。ランドマークは E1-2 の屋外 ID と同じく `campus_` で始まり、建物 ID は `campus` を含まないため、部屋 ID と衝突しない。

## 4. 対応表

全74件は [`E1-7-room-canonical-ids.csv`](E1-7-room-canonical-ids.csv) を正本とする。列は次のとおり。

| 列 | 内容 |
|---|---|
| `old_canonical_id` | 調査資料上の旧 ID |
| `new_canonical_id` | 本規則による canonical ID |
| `building_id`・`floor_id`・`type` | ID の各部分（§3 で一致を確認） |
| `display_name` | 資料上の名称。参加者向け表示名の正本ではない（正本は Studio の Spot 公開版。E2-5 §5.2） |
| `floor_source` | 階の出典（`id`：旧 ID のフロアトークン、`original_survey_floor_column`：原本の `階層` 列） |
| `alias_required` | 決定事項26 時点の案（全行 `yes`）。**本書では採用しない**（§6-2）。CSV は昇格元とのバイト一致（SHA-256）を保つため値を書き換えず、本表の注記で上書きする |
| `note` | 備考（`mb_2f_cl_001` の「原本から復元」のみ） |

決定事項26 が解決した主な問題（同 §3）:

- 教室と廊下が同じ `cr` で表されていた競合（`mb_f2_cr_2a` と `mb_f2_cr_001`）を、教室 `cl`・廊下 `cr` に分けて解消した。
- `ptb_f1_n_dtr_1` などが屋内ノードの形式（`_n_`）と衝突していたのを解消した。
- 大文字の混在（`ctc2_AKL_BNE` など12件）、区切り文字の多義性、フロアトークンの二系統（`mb_f2` と `mb_2f`）、階を持たない ID（26件）、連番形式の不統一を解消した。

## 7. 本書が前提とするもの・後続作業

本書は ID の規則と対応だけを定める。部屋の位置の公開には別の前提がある。

- **フロアの登録と屋内座標**：部屋を `room` Feature として公開するには、その `floor_id` が `nexus.floors` に登録され、代表点の WGS 84 座標が E1-5 のアンカー契約で求められている必要がある。v1.0 の屋内の対象は mb / ptb の承認対象階であり（#36、#85）、それ以外の建物（`ctc2`・`sab`・`ar` など）の部屋は、ID があっても位置を公開できない場合がある。主要6経路の ctc2 受付をどの目的地で表すかは、E1-4 改訂1 §8 のとおりデータ作成（#39）で決める。
- **最初の公開より前の移行（E2-5 O-3a 条件1）**：旧 ID は alias として登録しないため、次を新 ID へ揃えてから最初の公開を行う。
  - iOS の preview・テスト用データ（`apps/nexus-ios` の15ファイル。`MapPreviewFixtures.swift`、`TestSupport.swift` など。例 `mb_f2_cr_2a` → `mb_2f_cl_001`）
  - NexusStudio の取り込みサンプル `docs/samples/reference-sample.json` と、旧 ID を使うテスト（`PublishingTests.cs`、`ReferenceDataTests.cs`、`ReferenceEditingTests.cs`）
  - 実際の取り込みデータ（作業者手元）
- **外部参照の確認（同 条件2）**：E1-1 が ID の出典に挙げる「GitHub GeoJSON」が一般公開で旧 ID を含むかを、オーナーが最初の公開より前に確認する。
- **ID 台帳**：作業者手元の `Nexus_ID_Master_v2_draft.xlsx`（未リポジトリ化）の `proposed_canonical_id` 列と `Conflicts` シート（C-003・C-004・C-014）の更新は、原本の所有者が行う。
- **E1-2 の ID 体系表**：承認後、部屋（本書）とランドマーク（E1-4 改訂1）の行を追加する。

## 8. 採用しなかった案（決定事項26 §8 から引き継ぐ）

| 案 | 却下理由 |
|---|---|
| 旧 ID の局所符号を残す（`mb_2f_cl_2a` など） | `ctc2_AKL_BNE` のように `_` を含む符号を機械的に解析できず、区切り文字の多義性が残る |
| 教室を `rm`、廊下を `cor` にする（ID 台帳の旧提案） | D-21 が教室 `cl`・廊下 `cr` を指定した |
| 調査資料の `f2` 形式に統一する | E1-2 とスキーマの `floorId` は `{n}f` を要求し、`floor_id` が部屋 ID の接頭辞にならない |
| 階が不明な室に階を推測して割り当てる | 製品方針が禁じている。結果として推測は不要だった |
| 全室を汎用の `rm` に統一する | D-21 が教室と廊下の区別を求めている |
| 決定事項26 を昇格させず Studio だけに置く | MapDataset の ID 規則の正本は nexus-mobile の決定記録（E1-1〜E1-5）にあり、E1-4 改訂1 の `room.id` の規則を Studio 側の文書に依存させることになる |
