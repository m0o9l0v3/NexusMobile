# 本番データベースの採用・運用方針

- 決定日: 2026-09-19
- 決定根拠: リポジトリオーナーから、DBの採用方針・バージョン・運用方法の選定を委任された。
- 状態: 方針採用。PostgreSQL 18.6 / pgBackRest 2.59.1でローカルの初期構築・権限・API起動・暗号化バックアップ・指定時点復旧を検証済み。VPSとAWS S3への適用は未実施。
- 前提: VPSは選定済みだが現在ログインできない。DB製品は未選定だった。既存DBやデータの有無はログイン後に確認する。

## 1. 採用内容

| 項目 | 決定 |
| --- | --- |
| DB | PostgreSQL 18系 |
| 初期検証バージョン | 18.6（決定日時点の現行マイナー版）。実際の導入時に18系の最新修正版を再確認する |
| 実行方式 | 選定済みVPS上のDocker Engine + Docker Compose。DBコンテナ1台から開始 |
| ベースイメージ | Docker Official Image `postgres:18.6-trixie`。バックアップ機能を組み込んだ派生イメージを検証し、本番はdigestを固定する |
| DB名 | `nexus_admin`。管理APIと公開APIが共有するが接続資格情報・権限は分離する |
| 文字・日時 | UTF-8、DBおよび保存日時はUTC。画面表示はAsia/Tokyo |
| 永続領域 | 本番専用の明示名付き外部Docker volume。PostgreSQL 18のマウント先は `/var/lib/postgresql` |
| 接続 | APIとDBの専用Dockerネットワーク。ホストへの5432ポート公開なし |
| 管理アクセス | SSH経由のサーバー管理操作。DBをインターネットへ直接公開しない |
| 拡張 | v1初期構築ではPostGISなどの追加DB拡張は必須にしない。MapDatasetのpayloadは既定どおりtextで保持 |
| 検証環境 | 本番と同じPostgreSQL 18系の独立DB・volume・資格情報を使う |

PostgreSQL 18の公式サポート終了予定は2030-11-14。新規構築なので18系を採用し、将来のメジャー更新までの期間を確保する。既存コードのNpgsql/EF Core、PostgreSQL型のマイグレーション、コンテナ構成を生かせる。一方、現行Npgsql/EF Coreとの実接続互換性は検証用PostgreSQLで確認してから導入する。[公式バージョン方針](https://www.postgresql.org/support/versioning/)

18系では公式コンテナのデータ配置が17以前と異なる。既存の `postgres:15-alpine` のタグだけを変更しない。新規構築用の本番Composeを独立して作り、永続化と復旧を検証する。現行の2つの開発用Composeは本番設定として使わない。[公式イメージ仕様](https://hub.docker.com/_/postgres)

VPSはLinux上でDocker Engineを実行できることを構築条件とする。新規OS選択が可能ならUbuntu Server 24.04 LTSを基準とし、既存OSの再インストールは行わない。OS・CPUアーキテクチャ・メモリ・ディスク容量はログイン後に確認する。DBのメモリや接続数の設定値はその確認と負荷試験で確定する。

単一VPS構成では、VPS故障時にAPIとDBがともに停止する。初期運用は復旧手順を備えた単一構成とし、自動フェイルオーバーや無停止運用は提供しない。必要な稼働率が上がった時点でDB分離・冗長化を再評価する。

## 2. 権限と秘密情報

- スーパーユーザーは初期管理・緊急復旧専用。APIへ渡さない。
- スキーマ所有者はNOLOGINロールとし、移行専用ユーザーだけが所有者権限を使える構成にする。
- admin-apiの実行ユーザーには必要な表へのCRUD権限を付与し、DDL・ロール作成権限を付けない。
- public-apiは公開APIの処理に必要な表・ビューへの読み取り、および `visit_logs` へのINSERTだけを許可する。管理専用表や将来作成される全表への一括SELECTは付けない。
- 公開APIの専用接続設定は本番必須とし、管理API用接続へフォールバックさせない。
- パスワードはランダム生成し、リポジトリ・Issue・ログへ記録しない。サーバー上の権限を絞った秘密ファイルをCompose secretsとしてマウントする。Composeのファイルマウント自体を暗号化保管とみなさない。
- PostgreSQL認証はSCRAM-SHA-256。初期管理者の秘密は `POSTGRES_PASSWORD_FILE` で読み込む。API側の秘密ファイル読み込み経路も実装する。
- DBが別ホストへ移る場合は、証明書検証付きTLS接続を必須とする。

## 3. バックアップ・復旧

保存方式は **pgBackRest + AWS S3（東京リージョン）** とする。S3はVPS本体と独立した障害領域として使う。バケット・資格情報・課金の設定は構築時の作業であり、この決定では作成しない。

- PostgreSQL 18対応のpgBackRest安定版をDB派生イメージへ組み込み、バージョンとイメージdigestを固定する。公式postgresイメージに同梱済みとはみなさない。
- 週1回のフルバックアップ、その他の日は1日1回の差分バックアップを実行する。
- フルバックアップを5世代保持し、保持中のフルバックアップから復旧できる差分とWALを残す。週次が正常に成功している場合、約4週間以上の復旧範囲を確保する。
- WAL（更新履歴）を継続転送し、指定時点へ戻すPITRを利用する。`archive_timeout` は初期値5分。低頻度更新時にも転送が進むことを検証する。
- バックアップはpgBackRestで暗号化し、S3接続にはTLSを使う。復号キーはVPS外にも別管理し、復旧試験で取り出せることを確認する。
- S3は公開禁止・最小権限・バージョニング有効。pgBackRestが必要とする読み書き・世代整理の権限を限定し、S3の非現行バージョンは90日保持する。独自のS3期限設定で有効なバックアップやWALを途中削除しない。
- DB以外の復旧材料（Compose、イメージdigest、DB設定、秘密情報の復旧方法）も別途保全する。
- **損失を最大15分以内、復旧を4時間以内に抑えることを運用目標とする。** 接続障害・転送遅延・人の対応時間を含めて復旧試験で測る。現時点で達成済みの保証値ではない。
- 公開開始前、その後は月1回、独立した検証DBへの復元と指定時点復旧を試す。復元後にAPI読取、MapDatasetの版・checksum、主要件数を確認する。

WALとベースバックアップを組み合わせることで指定時点復旧を行う。単独の `pg_dump` だけではこの運用目標の代替にならない。[PostgreSQL PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)、[pgBackRest運用ガイド](https://pgbackrest.org/user-guide.html)、[pgBackRest設定](https://pgbackrest.org/configuration.html)

## 4. 初期構築・スキーマ更新

1. 検証用の空DBから、必要な全テーブル・インデックス・制約・権限・EF移行履歴を作成できる移行経路を整える。
2. CIで生成したSQLをレビューし、同じSQLを検証DBへ適用する。SQL成果物と適用前後の移行IDを保存する。
3. 本番では専用の移行処理を1つだけ実行する。API通常起動時の `MigrateAsync` とサンプルデータ投入を停止する。API起動はスキーマ整合確認にとどめる。
4. 初期データは出典・投入対象が明確な正式データだけを別途投入する。既存のサンプルSpotやイベントを本番へ流用しない。
5. 更新時はバックアップとWAL転送の正常性を確認し、初期運用ではメンテナンス時間を確保してAPIを停止する。SQL適用、動作確認、API再開の順に進める。
6. 適用失敗時はAPIを停止したまま原因を確認する。逆マイグレーションの自動実行はしない。変更前への復旧が必要なら、保全したデータから別volumeへ復元して確認後に切り替える。

本番でのスクリプト適用を基本とする方針は、レビュー可能なSQL生成と本番の起動時移行を区別するEF Coreの説明に沿う。[EF Coreの移行適用](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying)

## 5. 監視と更新

- VPSの起動時にComposeサービスを起動し、DBコンテナを障害時に再起動する。ヘルスチェック失敗も別途検知する。
- DB疎通、APIエラー、空き容量、接続数、バックアップ失敗、WAL転送失敗を監視する。disk使用率80%で警告、90%で緊急通知を初期基準とする。
- 日次バックアップが26時間以上成功していない場合、または未転送WALの最古が10分を超えた場合に通知する。単に更新がなくWALが生成されない場合と転送停止を区別する。
- 通知先を設定し、意図的な失敗で通知到達を確認してから公開する。
- 18系の修正版とベースOS修正を月1回確認し、検証後にメンテナンス時間内で更新する。重大なセキュリティ修正は優先して前倒し対応する。
- `latest` タグやコンテナの無人自動更新は使わない。更新ごとにバージョン・digest・検証結果を記録する。
- メジャー更新は別計画とし、dump/restoreまたはpg_upgradeを検証する。同じデータvolumeのままタグだけを次のメジャーへ変更しない。

## 6. 実装との不足分と次の作業

2026-09-19に以下の対応を実装し、隔離した実PostgreSQLで検証した。[構築手順](../production-database-runbook.md)と[検証記録](../verification/production-database-2026-09-19.json)を参照。

| 対象 | 対応状況 |
| --- | --- |
| 既存の移行が新規DB全体を作成できない | 過去の移行を有効化せず、残り12表を作る追加移行を実装。空DB・再実行・既存DB拒否を検証済み |
| 起動時のDbSeeder | Developmentだけに限定。本番は履歴・表・実行ユーザーの読み取り検査を実行 |
| 公開APIの接続と権限 | 専用接続を本番必須に変更。公開行のSELECT、監査ログINSERTと必要列だけのSELECTを実DBで検証済み |
| Composeと秘密情報 | 本番専用テンプレート、秘密ファイル読み込み、初期ロール作成を実装。本番イメージ公開・VPS設定は未実施 |
| バックアップと復旧 | ローカルの暗号化フル/差分・WAL・別volumeへの指定時点復旧を検証済み。AWS S3と本番規模の復旧試験は未実施 |

VPSログイン前に進めるのは、これらの実装と検証用DBでの試験、本番手順の作成。ログイン後はOS・リソース・既存データの有無を確認し、秘密情報・バックアップ保存先・通知先を設定してから本番適用する。

Issue #17の保存モデル実装と、この本番DB構築・運用準備は別の完了項目として扱う。方針決定だけを本番導入完了の根拠にしない。
