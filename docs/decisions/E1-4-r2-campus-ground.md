# E1-4 改訂2: 構内の地面（campus_ground）を加え、構内では Apple の地図の建物を見せない

- 改訂対象: [E1-4 GeoJSON スキーマ](E1-4-geojson-schema.md)（状態: 採用）と [`map-dataset-geojson-v2.schema.json`](../schemas/map-dataset-geojson-v2.schema.json)
- 状態: **採用**（2026-11-12、技術的意思決定者が PR #146 のマージにより承認）。判断事項 G-1〜G-4 は §7 の案のとおり決定。G-5（地面の見た目）は Figma で決める。E1-4 本文・JSON Schema への反映は §10
- 起案日: 2026-11-12
- 起点: M1 統合受入の予行（2026-11-12）で、Apple の地図に描かれた建物と、Nexus の建物の形（`building` の Polygon）がずれて見えた。利用者は、構内では Apple の地図の建物を見せない方向を選んだ（2026-11-12）
- 関連: E1-5（座標系）、[E3-1](E3-1-mapkit-adoption.md)（MapKit の採用）、M1-5・M1-6（[M1 決定記録](M1-scope-and-interim-decisions.md)）、E2-5（配信契約）、NexusStudio 決定事項31（地図の公開判定の承認済み設定）

## 1. 何が起きているか

Map は Apple の地図を背景に、Nexus の建物の形・ラベル・ピンを重ねて描く（E3-1）。予行のシミュレーターでは、Apple の地図の建物の形が、Nexus の建物の形よりおおむね南東へ数 m ずれ、大きさ・向きも少し違って見えた。同じ建物の輪郭が2つ、少しずれて重なるため、どちらが正しいのか分からず、地図を読む体験を大きく損なう。

## 2. どちらがずれているか

国土地理院の航空写真（地理院タイル「全国最新写真（シームレス）」）に Nexus の建物の形を重ねて比べた（2026-11-12）。

- 写真に写っている7棟（男子寮・食堂・アリーナ・管理棟・教室棟・実習棟・機体実習室）は、Nexus の形が屋根とおおむね重なった（目視で1〜3 m 程度）。
- 残りの7棟（CTC・CTC2・Da Vinci Hall・女子寮・格納庫A・格納庫B・技能審査棟）は、写真では空き地や駐車場で、写真のほうが古いと見られる。この比較では確かめられない（§8）。

したがって、ずれの主な原因は Nexus のデータではなく、Apple の地図の建物の形の側と考える。Apple の地図はこちらで直せず、報告しても反映の時期は分からない。

### Nexus の座標を Apple の地図に合わせない

Nexus の座標を Apple の地図の建物に合わせて動かすことはしない。

- 座標は WGS 84 の実際の位置とする（E1-5）。今後の現在地の表示や経路は、実際の位置で動く。
- Apple の地図に合わせると、実際の位置とずれる。Apple の地図が予告なく直ると、今度は Apple の地図ともずれる。

## 3. 方針

構内の範囲に不透明な「地面」を描き、その上に Nexus の建物・ピン（のちに経路）を描く。構内では Apple の地図の建物・道は見えず、Nexus のデータだけが見える。構内の外は Apple の地図のまま残し、周りの道路などで位置が分かるようにする。

SwiftUI の `Map` は、Apple の地図の建物だけを消す設定を持たない（`pointsOfInterest` は施設情報だけ）。そのため、上に地面を描いて覆う。

## 4. データ：地面の範囲を地図のデータに持たせる

### 4.1 新しい Feature 種別 `campus_ground`（案）

| 項目 | 値 |
|---|---|
| `id` | `campus_ground`（構内に1つ。案） |
| `geometry` | Polygon（穴を持たない。外環は反時計回り、RFC 7946） |
| `properties.feature_type` | `campus_ground` |
| `properties.scope` | `campus` |

- 地図に0個か1個。1個のとき、すべての `building` がこの中に入ることを validator が調べる（案）。
- 経路グラフ・目的地には関わらない。spot の解決元にもならない。

### 4.2 範囲を誰が作るか

**範囲は、オーナーが敷地の境界として作図・承認する**（NexusStudio 決定事項31と同じく、開発チームは値を作らない）。

Studio の承認済み設定にある `campusBoundary`（6頂点）は、ここには使わない。

- 役割が違う。`campusBoundary` は「地図の Feature がこの外にあれば公開を止める」ための許容範囲で、余裕を含めてよい。
- 航空写真に重ねると、西側の公道と南側の広い区画まで含んでいた。地面で覆うと、位置を知る手がかりになる公道まで消える。

作図は、建物と同じく QGIS の確定版 GeoJSON（原本）に加え、map-dataset CLI（`tools/map-dataset`）で GeoJSON 2.x へ取り出す。

### 4.3 版：2.1.0（minor）

- 既存の読み手が無視して安全な追加なので、minor にする（E1-4「バージョニングと互換性」）。
  - iOS は `feature_type == "building"` などで必要な Feature だけを選び、未知の種別では bundle を拒否しない。
  - E2-5 §6 も、マイナー版で加わった未知の項目は無視するとしている。
- ただし JSON Schema と Studio の validator は未知の種別を拒否する。schema・mobile の validator・Studio の validator（移植版）・CLI は同時に更新する。

## 5. iOS の表示

- `campus_ground` があれば、`MapPolygon` で不透明に塗り、建物より下に描く。無ければ今と同じ表示にする（地面を推測で作らない。建物の外接矩形などから作らない）。
- 塗りの色・枠・構内の外との境目の見た目は、Figma で決めて承認を得る（M1-6 と同じく node ID・承認者・承認日を記録する）。
- 地面の上に Apple の施設名や道路名が重ならないことを、シミュレーターで確かめる（`MapPolygon` は Apple の地図の文字より下に描かれうる。重なる場合は §7 G-4 で扱う）。
- 通信断でタイルが読めないときも、地面・建物・ピンは表示される（E3-1 の条件を保つ）。

## 6. 取り込む順序

1. 本書の判断（§7）
2. オーナーが範囲を作図・承認する（原本）
3. nexus-mobile：E1-4 本文・JSON Schema 2.1.0・正常例・validator・map-dataset CLI
4. NexusStudio：検証器（移植版）・取り込みの 2.1.0 への対応
5. Figma：地面の見た目の承認
6. iOS：地面の描画（未知の種別を無視するので、3・4 より先に出しても壊れない）
7. 隔離環境で、Studio で公開した地図から表示まで確かめる（M1 の予行と同じ経路）

## 8. 範囲外・残ること

- 写真で確かめられなかった7棟（§2）の形の確認。入口の GPS 実測（`map-data/normalized/entrances.csv`）との照合か、現地での確認が要る。地面で Apple の地図を覆っても、Nexus の形そのものが違っていれば直らない。
- 構内の道・駐車場の表示。地面で覆うと見えなくなる。経路（M2）の歩道を描くまで、構内は建物とピンだけになる。
- Apple への地図の修正の報告。してよいが、本書の解決策には数えない。

## 9. 却下した選択肢

| 選択肢 | 却下の理由 |
|---|---|
| Nexus の座標を Apple の地図に合わせて動かす | 実際の位置（E1-5）とずれ、現在地・経路と合わなくなる。Apple の地図が直るとまたずれる（§2） |
| 地図の背景を地理院タイルなどに差し替える | SwiftUI の `Map` は背景の差し替えに対応せず、UIKit の `MKMapView` への作り直しになる（E3-1・M1-5 に反する）。通信断の扱いも難しくなる |
| Apple の地図の色を薄くし、Nexus の建物の塗りを濃くするだけ | 形がはみ出した部分のずれは残る。応急処置にはなるが解決にならない |
| 地面の範囲を iOS が持つ、または建物の外接矩形から作る | 地図の版と範囲が別々に変わる。推測で作った範囲は敷地と合わず、公道を覆うか敷地を覆い切れない |
| `campusBoundary`（公開判定の許容範囲）を地面に流用する | 役割が違い、西側の公道まで覆う（§4.2） |
