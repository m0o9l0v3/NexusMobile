## 採用方針

iOS の `Features/Route/Engine/` に、公開地図を読み取る不変の `RoutingGraph` と、グラフを入力に取る `RoutingEngine` を置く。グラフは地図の版ごとに構築でき、探索中に通信や位置情報の取得を必要としない。ノード ID を指定する探索と、目的地 Feature の ID を指定する探索は入口を分けた。

### アルゴリズムの比較

| 案 | この地図での判断 |
| --- | --- |
| Dijkstra ＋二分最小ヒープ（採用） | 距離・時間は非負で、正式入口だけでも重み 0 を扱う必要がある。出発点から探索し、目的ノードの最良候補を取り出した時点で経路を確定できる。 |
| A* | 直線距離や標準歩行速度から、配信された距離・時間の下界が得られる保証はない。妥当なヒューリスティックとその検証が増える。 |
| Bellman–Ford | 負の重みを扱えるが、この契約で負値はデータの不備にあたる。繰り返し全辺を調べる利点がない。 |
| Floyd–Warshall | 全ノード対を前計算する時間とメモリが必要で、通行方針・評価指標ごとに結果も異なる。端末で要求された1経路を求める用途には重い。 |

### 配置の比較

| 案 | このアプリでの判断 |
| --- | --- |
| `apps/nexus-ios/Nexus/Features/Route/Engine/`（採用） | Swift の bundle 型をそのまま読める。Foundation のみを使い、地図描画や SwiftUI への依存を持ち込まず、既存の NexusTests で検証できる。 |
| `packages/shared/` | TypeScript と Swift の境界が増え、公開地図の型と探索結果を言語間で受け渡す必要がある。 |

## グラフと探索結果

- `walking_path` は `from_node_id` → `to_node_id` の向きで登録する。`bidirectional` が真なら逆方向にも通れる。距離・時間の重みと合計には `distance_m`・`estimated_seconds` を使い、LineString は各ステップの進行方向に並べる。
- `formal_entrance` は屋外と当該建物・階の屋内ノードを結ぶ双方向の辺で、距離も時間も 0 とする。入口の閾値座標、所属、代表入口フラグ、表示名、通行属性、表示用営業時間を保持する。
- `.standard` は `accessible`・`not_accessible`・`unknown` を通れる。`.accessibleOnly` は `accessible` だけを通れる。入口・抽象遷移も同じ規則に従う。
- ノード・辺・目的地の ID は大文字小文字を区別して照合する。重複した既知 Feature の ID は同名の候補をすべて除く。別 ID の並列辺はそれぞれ保持する。自己ループ、未知端点、非有限値、歩行辺の非正の重み、所属の異なる歩行辺などは除外し、ID と理由を `skippedDiagnostics` に返す。未対応の Feature 種別は読み飛ばす。
- 各隣接リストを（到着ノード ID、辺 ID）で昇順に並べる。候補同士は **主指標、副指標、辺数、出発点からの辺 ID 列の辞書順** で厳密に比較する。距離優先（既定）では副指標が時間、時間優先では副指標が距離になる。辺数は重み 0 の入口を通っても増えるため、入口を往復した候補が元の候補に勝つことはない。
- ヒープの追加・取り出しに必要な比較回数はキュー長に対して対数。決定的な同点処理のため候補には辺 ID 列を保持する。列を延長するコピーと同点時の辞書順比較は経路長に依存する。
- 同じノードは孤立していても `.samePoint`（0 m・0 s、ノード1個、ステップ0件）。通常経路の `traversedFloorIDs` はノード列から屋外を除き、連続する同一階を1つに畳む。入口の両端は別ノードなので、距離 0 でも通常経路になる。
- 有効辺の向き・通行制限を外した連結成分を構築時に求める。別成分は `.disconnected`、同じ成分でも方向・通行制限で行けない場合は `.unreachable`。未知ノード・未知目的地は専用の失敗理由を返す。

## 目的地の到達ノード（E1-4 改訂1 §4.3・§4.4・§5・§8）

| 目的地 | 解決規則 |
| --- | --- |
| 部屋 | 同じ建物・同じ階の屋内 `destination` ノードを `access_node_id` で指定する。 |
| ランドマーク | 屋外の `destination` ノードを `access_node_id` で指定する。 |
| 建物 | 明示された同じ建物の屋内 `destination` ノードを優先する。指定が無い場合だけ、唯一の代表入口の外側ノードを採る。 |
| 正式入口 | 同じ建物の屋内からは内側、屋外または別建物の屋内からは外側を採る。 |

明示的な解決は `resolveDestinationNode(for:approach:)` を使う。ノードから目的地への探索は出発ノードの所属で入口の側を決める。両端を目的地 ID で指定する場合、出発側の正式入口は既定で外側、`approach` で同じ建物の屋内を指定すれば内側になる。その後、解決した出発ノードから終点の側を判定する。

到達ノード指定の欠落（建物では代表入口も無い場合）は `missingAccessNode`、不正な参照は `invalidAccessNode`、代表入口の重複は `ambiguousPrimaryEntrance`。いずれも `notRoutable` として返す。ノード ID・歩行辺 ID は目的地の検索対象に含めない。欠落した到達ノードを補うために名前・近傍点・非代表入口を使うことはない。
