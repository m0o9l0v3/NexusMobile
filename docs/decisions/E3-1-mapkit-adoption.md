# E3-1: SwiftUI の MapKit で構内地図を描く

- 移行元ID: E3-1 / 区分: E3 / Issue: #24
- 依存: M1-5（[`M1-scope-and-interim-decisions.md`](M1-scope-and-interim-decisions.md)）、E1-4・E1-5、E2-5
- 判断日: 2026-10-24（採用は M1-5、2026-10-23。本書は採用理由・通信断の制約・検証結果の記録）
- 判断者: リポジトリオーナー（技術的意思決定者）
- 状態: 採用

## 採用方針

参加者向け iOS アプリの構内地図は、SwiftUI の MapKit（`Map`・`MapPolygon`・`Annotation`）で描く。外部の地図 SDK は追加しない。

建物の形・建物ラベル・地点のピンと地点名は、bundle（E2-5）から得た座標をもとに**アプリが描く**。Apple の地図タイルは位置の手掛かりとしての背景にすぎず、タイルが読めなくても構内の表示は欠けない。

## 理由

- OS 標準のフレームワークで、依存の追加・ライセンス・更新の追従が要らない。技術的な判断の移譲先がない体制（`CLAUDE.md`）で、保守する部品を増やさない。
- E1-4 の GeoJSON（WGS 84、`[経度, 緯度]`、E1-5）を変換なしで緯度経度として渡せる。
- 建物の Polygon とピン（Point）の描画、ズーム・回転・縮尺表示が SwiftUI の宣言的な API で揃う。
- 比較を省いた理由と、#24 の受入条件の読み替えは M1-5 と #24 本文の追記による。

### 選ばなかったもの

| 案 | 選ばなかった理由 |
|---|---|
| 外部の地図 SDK（Mapbox・Google Maps など） | 依存・API キー・利用規約の管理が増える。通信断で構内を描く点では MapKit と差がない（どちらも構内の形は自前のデータから描く） |
| 構内図を自前で描く（Canvas・SVG） | 拡大縮小・回転・周辺の道路との位置関係を自作することになる。通信断の表示だけなら成り立つが、M1 の範囲では作る量に見合わない |

## 通信断のときの制約

2026-10-24 の検証（下記）で分かったこと：

1. **地図タイルは表示されない。** 背景は方眼だけになり、道路・川などの周辺の地物は見えない。以前に表示したタイルが端末に残っていれば出ることがあるが、それを当てにしない。
2. **`Annotation` の title（MapKit が描く名前）は表示されない。** 通信があるときはピンの下に出ていたが、通信断では消えた。地図の文字と一緒に描かれるためと考えられる。このため、ピンの地点名と建物ラベルは title を使わず、Annotation の中身の View としてアプリが描く（`.annotationTitles(.hidden)`）。
3. `MapPolygon`、Annotation の中身の View（ピンの図形・アプリが描く文字）、`MapCompass`・`MapScaleView` は通信断でも表示される。
4. 左下の Apple のロゴは通信断でも残る。「法律に基づく情報」のリンクは通信断では出なかった。

## 検証（#24）

### 方法

- 描画面：`MapKitMapSurfaceView`（`apps/nexus-ios/Nexus/Features/Map/Views/`）。既存の注入境界 `MapSurfaceProvider` の実装で、本番の既定は「構内地図は未提供」のまま変えていない。
- データ：DEBUG 専用の検証用データ `CampusMapContent.offlineCheck`。E1-1 の14棟の canonical ID・表示名に、格子状に並べた**仮の形状・位置**を与え、建物 Spot のピン14本と、部屋・ランドマークのピン各1本を加えた。実際の建物の形・配置とは一致しない。
- 起動：DEBUG ビルドの起動引数 `-NexusPreviewData -NexusMapKitCheck -NexusPreviewScreen map`。
- 通信断：Mac の Wi-Fi を切った状態で、地図の保存が空の新しいシミュレーター（iPhone 17 Pro、iOS 27.0、`simctl create` 直後）を起動し、アプリを入れて約30秒後と約45秒後に撮影した。撮影の前に、外部（www.apple.com）と Apple の地図タイルのホストへ通信できないことを確かめた。

### 結果

| 項目 | 通信あり | 通信断 |
|---|---|---|
| 地図タイル（道路・川など） | 表示 | 表示されない（方眼のみ） |
| 14棟の形（`MapPolygon`） | 14棟すべて表示 | 14棟すべて表示 |
| 建物ラベル（アプリが描く文字） | 14棟すべて表示 | 14棟すべて表示 |
| ピン（建物14・部屋1・ランドマーク1） | すべて表示 | すべて表示 |
| ピンの地点名（Annotation の title） | 表示 | **表示されない**（制約2） |
| ピンの地点名（アプリが描く文字に変更後） | すべて表示 | すべて表示 |

結論：通信断でも、建物の形・ラベル・ピンと地点名は表示できる。M1-5 を見直す必要はない。

### この検証で確かめていないこと

- **正式な14棟のデータでの表示。** 形・位置が bundle と一致することは、M1 の統合受入（M1 決定記録 §5.1 の1・6）で、Studio が公開した実データを使って確かめる。
- 選択・地点詳細への遷移、ラベルとピンの重なりの扱い、ズームに応じた表示の切替。いずれも #26・#85 で、#84 の承認版に沿って作る。
- 建物ラベルの位置を何から決めるか。検証用データでは明示した座標を与えている。→ 下記「建物のラベルとピンの位置」で決定（2026-10-24）。
- 実機（iPhone）での表示。

## bundle から描く内容の組み立て（#26）

`CampusMapContent(bundle:)`（`apps/nexus-ios/Nexus/Features/Map/Data/CampusMapContent+Bundle.swift`）で、検証済みの bundle から描画面の入力を作る。

- **建物**：`map.geojson` の `building` Feature すべて。外周と、中庭などの穴（Polygon の内側の環、E1-4）を持ち、`MKPolygon` の内側の多角形として描く。ラベルは `building.properties.name`（M1 決定記録 §5.1 の1）で、無ければラベルを出さない。
- **ピン**：`placement` のある spot すべて（bundle の順）。名前は `spots[].name`。位置は `placement.point`。`placement` が null の spot は置き場所が無いためピンを出さない（E2-5 §5.2「推測で埋めない」）。
- 階による絞り込みはしない（すべての階の部屋を1枚の地図に置く）。階の切替は #40。

### 建物のラベルとピンの位置（2026-10-24 利用者決定）

建物の spot は `placement.point` が null（E2-5 §5.2）で、地図データにもラベルの位置は無い。このため **iOS が描画のためだけに形状から計算する**。計算した値は bundle にも契約にも書き戻さない。建物のラベルと、建物の spot のピンは同じ点を使う。

1. 外周の面積重心が、建物の内側（外周の内側かつ穴の外）にあればそれを使う。
2. L字型や中庭のある建物で重心が外に出る場合は、重心と同じ緯度の水平線が建物の内側を通る区間のうち、最も長いものの中点を使う（同じ長さなら西側）。
3. 形が潰れていて求まらない場合は、外周の範囲の中心を使う。

構内の建物は小さいため、経緯度をそのまま平面として計算する。

| 選ばなかった案 | 理由 |
|---|---|
| 建物の `access_node_id` が指すノードの座標 | `access_node_id` は null のことがある（経路グラフが未公開の間など）。その建物はラベルとピンを出せず、M1 の統合受入（14棟すべて表示）を満たせない |
| 地図データ（E1-4・Studio）に代表点を足す | 契約の改訂と Studio の実装が要り、NexusMobile だけでは進められない。表示の都合を公開データの正本に持ち込むことにもなる |

ラベルと建物のピン（とその名前）が同じ点の近くに重なる見た目の調整は、#84 の承認版に沿って #85 で行う。
