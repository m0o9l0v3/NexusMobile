## 2. admin-api / public-api の責務境界案（v1.0）

**admin-api に閉じる責務**
- 管理者認証（`/admin/auth/login`）、JWT issuance/revocation（`issued_tokens`/`revoked_jti`、`TokenRevocationController`）
- Spots / Events / OcDays の CRUD、`GET /admin/spots/{id}/qr`（resource link QR PNG 生成）
- 運用ログ閲覧・チェーン検証（`/admin/logs/recent`・`/admin/logs/verify`）
- **hidden beta**: QR issue 発行/失効（`QrIssuesController`）、ワンタイムコード生成/引換（`EventOneTimeCodesController`・`OneTimeCodeRedemptionController`）、`/q/{token}` snapshot 表示（`PublicQrController`）

**public-api に閉じる責務**
- 参加者向け read model: `/api/spots/public`, `/api/spots/by-code/{code}`, `/api/events/today`, `/api/nearby`, `/api/navigation/*`, `/api/floors`, `/api/routes`, `/health`
- 匿名ログ受信: `POST /api/logs(/batch)` → `visit_logs` INSERT（唯一の例外書き込み。`LogPersistenceService.cs`）

**public-api に入れてはいけない責務（現状も入っていないことを確認済み）**
- 認証・トークン発行/失効・チェックイン状態管理・参加者識別（プロフィール）
- QR issue の発行・失効・token lookup（`/q/{token}` 相当の機能を public-api に移設しない）
- `visit_logs` 以外へのあらゆる書き込み

**hidden beta QR の置き場所**
- token 型 QR（`/q/{token}`、qr_issues）は **admin-api 内に現状のまま留める**。public-api へ移さない。v1.0 では管理 UI・README の主要導線から外す（→ `4, タスク NEX-A7）。
- resource link 型 QR（spot code → `/?code=XXXX`）は v1.0 の正式機能として残す。

**判断根拠**: `Program.cs:65-70` の ApplicationParts 限定により、コードレベルの分離は既に成立している。境界侵犯は「DB ロールが認証/QR 系テーブルまで読めること」（`5）と「ドキュメントがチェックイン機能を参加者導線として説明していること」（`3）の 2 点であり、endpoint の移動は不要。

## 3. QR hidden beta 方針を反映した README/docs 更新案

**新設: `docs/qr-hidden-beta-v1.md`（方針の single source of truth）**

見出し案:
1. 「v1.0 における QR の位置づけ」— QR は公開リソースへの resource link。認証・チェックイン・参加者識別ではない
2. 「v1.0 で正式提供するもの」— spot code QR（`/admin/spots/{id}/qr` → `/?code=XXXX` → `GET /api/spots/by-code/{code}`）
3. 「hidden beta（提供するが主要導線に出さない）」— `/q/{token}`、QR issue 発行/失効、ワンタイムコード生成/引換
4. 「v1.0 範囲外」— ワンタイムQR・参加者別QR・token issuance/revocation・チェックイン状態管理
5. 「visit_logs との関係」— QR 経由アクセスは将来 `eventType = qr_scan` として記録できる余地を残す（サーバー側は既に受理可能）

## 5. PostgreSQL readonly role の権限見直し案

**現状**: `20260702120000_AddPublicApiReadOnlyRole.cs` が `SELECT ON ALL TABLES` + `ALTER DEFAULT PRIVILEGES`(将来テーブルも SELECT) + `visit_logs` INSERT。

**リスク**: public-api プロセスが侵害された場合（SQLi・RCE・依存汚染）、読める必要のない `issued_tokens`（jti・subject）・`revoked_jti`・`qr_issues`（token hash・snapshot）・`one_time_login_codes`（code hash）まで漏えいする。ハッシュ保存とはいえ、認証系メタデータの露出は攻撃の足掛かりになる。また default privileges により将来の機微テーブルが自動的に読めてしまう。

**public-api が実際に必要とする権限（コード全量 grep で確定）**:
- SELECT: `spots`, `events`, `visit_logs`
- INSERT: `visit_logs`
- **`visit_logs` の SELECT は必要**（削ってはいけない）: `LogPersistenceService.cs:55-59` がハッシュチェーンの prev_hash を `visit_logs` から SELECT するため。これが「visit_logs の SELECT は必要か慎重に判断」への回答。
- `oc_days` は現状 public-api のコードから参照されていない（grep 確認済み）。将来 read model で使う想定があるため、allowlist に**含めてもよい**が現時点の必要権限ではない → 推奨: 含めない（必要になったら migration で追加）。
- navigation 系は JSON ファイル読みで DB 不要。
- `__EFMigrationsHistory`: public-api は `Migrate()` を呼ばない（`Program.cs` 確認済み）ため不要。

**変更案（allowlist 方式）**: 新 migration `RestrictPublicApiReadOnlyRole` を追加し、
1. `REVOKE SELECT ON ALL TABLES IN SCHEMA public FROM nexus_public_readonly;`
2. `ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE SELECT ON TABLES FROM nexus_public_readonly;`
3. `GRANT SELECT ON TABLE spots, events, visit_logs TO nexus_public_readonly;`
4. `GRANT INSERT ON TABLE visit_logs TO nexus_public_readonly;`（冪等に再付与）
5. Down は現行の ALL TABLES + default privileges へ戻す。Npgsql ガード（`ActiveProvider` チェック）は既存 migration と同型。

**認証系/QR発行系テーブル**: `issued_tokens`, `revoked_jti`, `qr_issues`, `one_time_login_codes`, `departments`, `exhibits`, `open_campus_timeslots`, `timeslot_exhibits`, `oc_days` は **SELECT 付与しない**（revoke で外れる）。

**付随更新**:
- `docs/deploy-public-api-readonly-role.md` `3 smoke test に「失敗するはず: `SELECT count(*) FROM issued_tokens;` / `SELECT count(*) FROM qr_issues;`」を追加し、`SELECT ON ALL TABLES` の記述を allowlist に更新
- `apps/public-api/README.md:13-17` の「SELECT on all tables」を allowlist 記述へ
- 運用注意: 今後 public-api が新テーブルを読む場合は migration での GRANT 追加が必須になる（default privileges を外すトレードオフ）。単独意思決定体制なので explicit grant を推奨。
